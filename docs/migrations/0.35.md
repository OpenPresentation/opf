# Updating from 0.34 to 0.35

0.35 changes little that a deck or a host has to act on. For a deck, run `opf fix deck.opf.json -i`, then validate (`opf validate deck.opf.json --fail-on warning`). Each deck change below is reported, and most come with a fix marked safe (it loses no content and writes valid OPF): `opf fix` applies those, in the deck and in its own layout records, including the stale copies of built-in layouts in a self-contained deck ([below](#self-contained-decks-embedded-copies-of-built-in-layouts)), and lists each one, marking those that change how a slide draws (`changesDrawing`, below: `rename-layout` from `agenda-split` or `flow`, `remove:contentDirection`, `remove:chartPrimary` and some `remove:listColumns`); every other safe fix keeps the 0.34.2 drawing. By default it applies only the fixes of the checks that repair the document; an audit's fix (accessibility, content) waits for `--audits`, and a fix that restyles content, such as a new text color, is not safe at all. It validates again after each round of fixes, since an error in the deck's own keys stops the accessibility, layout and content checks, so findings such as `opf/region-unknown` appear only once it is fixed. A fix that needs a choice (such as `role: "secondary"`) is never applied: `opf validate` reports it with its fixes, and `opf fix` lists it in `fix.unsafe`. From code, core's `fix(deck)` does the same.

The slide composes automatically meanwhile. A catalog of your own may still define a layout named `flow`. |

A longer list, an entry of three or more words or over 24 characters, a description, an icon, numbering, nested entries, or a list beside other blocks draw as before. |
| A block pinned to a region of a built-in layout by its 0.34 name (`"region": "notes"`, Markdown `region=notes`) | The built-in layouts use seven standard body-region names: `body`, `lead`, `aside`, `media`, `first`, `second` and `third` (table below). The finding names the new region ("OPF 0.35 renamed region 'charts' of the built-in layout 'chart' to 'body'") and offers the safe fix `rename-region`, which writes it; or remove the pin where plain binding places the block. A block drawn as the automatic foot band (the comparison's `verdict` text) is reported too. Every layout draws as before. |
| `design.contentDirection` (`horizontal` or `vertical`) on the deck or a slide | Removed. Delete it (`opf validate` reports `opf/schema` at the key, says what replaced it and offers the safe fix `remove:contentDirection`, marked `changesDrawing`: it deletes the key and writes nothing in its place, and removes the `design` object when the key was all it held). On an automatic slide write `composition.mode`: `"row"` for `horizontal`, `"column"` for `vertical` (a deck-wide value becomes a `composition.mode` on each slide that needs it). On a slide with a layout, the layout's regions say it: the built-in `process` lays its steps in a row as before; for another layout, use a custom record whose region has `"flow": "row"` or `"column"`. Until it is deleted the key fails the schema and composition ignores it. |
| `design.chartPrimary` (`none`, `start`, `end`, `top`, `bottom`) on the deck or a slide | Removed. Delete it (`opf/schema` at the key, safe fix `remove:chartPrimary`, marked `changesDrawing` on the deck, a slide or a theme; in a layout record, where it never applied, it is not). It drew only on automatic slides (a slide with a layout ignored it). To keep the split, set the slide's `composition`: `start`: `composition: { "mode": "row", "weights": [3, 2] }` with the chart first in `blocks`; `end`: `"weights": [2, 3]` with the chart last; `top` and `bottom`: the same two with `"mode": "column"`; in each, several other blocks go in one group (`{ "blocks": [...] }`); `none`: delete it. That keeps the split: the same sides at the same 3:2 widths. Inside their side the other blocks can be placed or sized differently, so look at the slide. Drawn against 0.34.2, a chart with a table, with a list of four or more entries, or with a list and a text came out the same. A chart with one text block did not: `chartPrimary` grew that text and centered it beside the chart, and a composition sets it at its own size at the top of its side (give its runs a `fontSize` to keep it large). Two text blocks, a two-entry list and a metric sometimes differed. The `chart-beside` layout is not a replacement: it has no region for a table (`opf/layout-unplaced`), and with `design.mirror: true` it does not draw what `end` drew. Without it an automatic slide gives a short chart among other blocks its own track (LH-49) as before. |
| A long list (more than 6 entries) on a layout slide | It flowed into columns only on the `agenda`, `faq` and `list` layouts (their regions set `listColumns: "auto"`). It now may on any layout, in a region without an `arrangement` (or with `numbered`, the agenda's): up to three columns when one column does not hold it at its starting size, kept only when the columns set it at least as large as one column would and do not overflow where one column fits. A region made for a list (`list` its first accepted kind: `agenda`, `faq`, `list` and a custom record's list region) keeps LH-184's rule that columns may come out up to a type-scale step under one column whose lines would run past the reading measure; there, columns that overflow now give way to one column that fits at least as large. A list in a diagram region, a `steps` region or below a layout's grid keeps one column. No gallery layout preview, example slide or layout golden draws differently. Write `"columns": 1` on the list to keep it in one column, or `2`, `3` or `"auto"` to choose. Nothing to change. |
| A list in a row of cells sized by `composition.weights` whose cell was narrower than its longest word | The word broke inside it. The row is rebalanced: the list's cell widens to the narrowest width at which every word holds at the list's size (or larger) and the other cells give that width up while none of their text is set smaller; when they cannot, the blocks are stacked in one column, kept only when no block reads smaller there. The list is never set smaller. Nothing to change. |
| A slide key that placed content in a cell of the slide's 3 x 3 grid (a promoted region): `"top:start": { "text": "..." }`, and the other 47 (`start`, `center`, `end`, `start+center`, `center+end`, `start+center+end`, `top`, `middle`, `bottom`, `top+middle`, `middle+bottom`, `top+middle+bottom`, and each of the six row bands with a colon and each of the six column bands: `middle+bottom:center+end`) | A block of the slide's `blocks` names its cell with `region`, the key a block uses to pin itself to a layout region: `"blocks": [{ "region": "top:start", "text": "..." }]`. The slide keys are removed: `opf/schema` at the key says what replaced it and offers the safe fix `cells-to-blocks`, which moves every cell key of the slide into a block that names its cell, in reading order of the cells, each payload as written (a group payload stays one group block). `opf fix deck.opf.json -i` applies it (with the other safe fixes, round after round). The slide draws exactly as before. Until it is fixed the slide draws without that content. A key written like a cell (`left`, `start:top`, `bottom+middle`) is reported the same way and the fix names the cell it means. |
| Blocks in cells: the rules | A slide places every block in a cell or none: a block that names none beside one that does is `opf/schema` ("a slide places every block in a cell of its grid or none"). Two or more blocks that name the same cell stack in it in source order, as a group's blocks would; never an error. Two different cells may not overlap (`opf/schema` at the later block's `region`, as overlapping keys were). Only a root block names a cell; a block in a cell takes no `placement` (`opf/image-placement-invalid`). A `region` written like a cell but not one gets the grammar as help and the fix `change-to:<cell>`. |
| A slide with a `layout` and cell keys | Through 0.34 the cells composed the slide and the layout's regions were not used, but the layout still reached it: its `design` keys (read as the layout's: a centered layout centers only short text), its color variant (a section's accent, a closing's brand surface), its `composition`, and for the quote, statement and closing records rules that read their regions (larger text). A cell word now names no region of a layout (`opf/region-unknown`; the block binds by kind). `opf fix` migrates such a slide with `cells-to-blocks`, safe here when it keeps the drawing: it removes `layout`, names the cells, and writes on the slide's design what the layout gave it (`design.variant`, `titleAlignment`, ...), which it checks by composing the slide both ways. Checked with a slide of two column cells on each of the 40 built-in layouts of 0.34 (0.35 has 38: `flow` and `agenda-split` are gone), 36 of those slides are fixed this way and draw exactly as on 0.34.2. The rest (`quote`, `statement` and `closing`, whose regions shaped the cells, and a `metrics` slide whose centered alignment a slide cannot say unless the deck sets one) are left: the finding carries `cells-to-blocks` without `safe` (remove the layout; the drawing changes a little) and `cells-to-layout-blocks` (keep the layout; the blocks bind to its regions), and its help says why. |
| Markdown `<!-- block: region=top:start -->` | Unchanged in the source. It reads as the block's `region` (it read as a slide key). |

### Self-contained decks (embedded copies of built-in layouts)

`opf embed` (core `embed()`) copies every built-in layout a deck uses into `catalogs.default.layouts`, as the release that ran it published the record. 0.35 changed the keys of those records (`flow: "none"`, `listColumns`, `sequence`, `pyramidDirection`, the `flow` arrangement, `design.contentDirection`) and an earlier copy can also carry 0.34's `left` and `right` alignments, so such a copy fails the 0.35 layout schema: every deck made self-contained before 0.35 (pptx.gallery's how-to decks, pptx.dev's saved and starter decks, openpresentation.org's tutorials) is invalid, and `opf convert` stops with `invalid-document`.

| What | In 0.35 |
| --- | --- |
| The fix | `opf fix deck.opf.json -i` applies the safe fix of each stale copy (`use-current-record` or `rename-layout` where it is safe, else each key's) with the deck's other safe fixes; or `opf embed deck.opf.json -i`, which refreshes the copies alone. It makes each stale copy valid without changing what it draws, writes the deck and lists the copies in the report's `embed.refreshed` (`how`): an unedited copy of the 0.34 release takes the current record (`current`), and each pin of its slides the region's 0.35 name; an unedited copy of a layout 0.35 removed moves its slides to the replacement and drops the copy (`renamed`, as `rename-layout` does; an `agenda-split` slide then draws its title column at two fifths of the width, where it was half); any other copy (an earlier release, or one you edited) gets the safe fix of each key (`converted`), keeping its own drawing and region names. Then validate again. It still refuses a deck with other invalid content, listing it; fix that and run it again. |
| `opf validate` | Each error in the copy says what it is. Its message starts with it ("catalogs.default.layouts.cover is an unedited copy of OPF 0.34's release of the built-in layout 'cover': must be equal to one of the allowed values"), and its help says it in full: "catalogs.default.layouts.cover is an unedited copy of OPF 0.34's release of the built-in layout 'cover'; 0.35 changed the keys of the built-in records, so the copy fails the 0.35 layout schema." (or "of an earlier release", or "an edited copy"), then what replaced the key. It carries the key's own fix (`use-max-1`, `remove:listColumns`, `use-arrangement`, `use-inverted-pyramid`, `use-pyramid`, `rename-arrangement`, `remove:contentDirection`, `change-to:start`) and `use-current-record`, which replaces the copy with the current record and renames the pins of its slides. |
| What is safe | Decided by the copy's content hash against every version of the built-in record released before 0.35. `use-current-record` is safe for an unedited copy of the 0.34 release: 0.35 converted exactly that record, so the current one draws the same. For a copy of an earlier release it is offered, not safe (the current built-in draws differently, for example `cover` with its title at the bottom over a rule), and for an edited copy it drops the edits. A copy of `flow`, `vertical-flow` or `agenda-split` gets `rename-layout`, safe when unedited. |
| A slide on a stale copy | `opf/unresolved-reference` says "Layout 'cover' is embedded in catalogs.default, but the record fails the layout schema: see the opf/catalog-record findings at /catalogs/default/layouts/cover." with the same cause and fix. It said the layout was not embedded. A record of the deck's own (`catalogs.custom`) gets the same message and its keys' fixes; `opf embed` does not change it, `opf fix -i` applies the safe ones. |
| `opf convert`, `opf paginate` and the other writing commands | Still refuse the deck (`opf fix -i` first). When findings carry a safe fix, their error names it ("2 findings carry a safe fix: `opf fix <deck> -i` applies them, then validate again."), and it ends "The deck embeds copies of built-in layouts from before OPF 0.35 (cover): `opf embed <deck> -i` refreshes each one it can without changing what it draws; validate again after it." |
| `--check` | `opf embed deck.opf.json --check` exits 1 when a copy would be refreshed. |

## Custom layout records

`opf fix deck.opf.json -i` applies the safe fixes below to the deck's own records (`catalogs.custom`, which `opf embed` does not change) and leaves the others for you, listed in `fix.unsafe`.

| --- | --- |

The gallery `dashboard` layout's `kpis` region is `supporting` now and draws as before. |
| A region with `"sequence": "steps"` or `"sequence": "numbered"` (step badges) | `"arrangement": "steps"` or `"arrangement": "numbered"` (safe fix `use-arrangement`). A region has one `arrangement`: a sequence (`steps`, `numbered`) or a diagram, never both. |
| A region with `"arrangement": "flow"` or `"arrangement": "vertical-flow"` | `"arrangement": "process"` or `"arrangement": "vertical-process"` (safe fix `rename-arrangement`), PowerPoint's names (Basic Process and Vertical Process). The gallery's `flow` layout is gone (its `process` layout draws a short list as Basic Process) and `vertical-flow` is `vertical-process` (Decks, above). |
| A region with `"arrangement": "steps"`: its lone list of 3 to 6 entries of one or two words drew as a row of chips joined by arrows | Its lone list of 2 to 8 entries of one level, each of one or two words and at most 24 characters, without numbering, descriptions or icons, draws as Basic Process in the region's whole cell where Basic Process holds every entry at the size its steps would have or larger; otherwise the list draws as steps. | An id `auto` was refused for a layout record | Allowed: `auto` is an ordinary id. |

A custom record that named a region `verdict` loses that rule; name it `aside` beside `first` columns to keep it. |

## Hosts and scripts

**Repair before drawing.** The 0.35 renderer's `toSvg` throws `invalid-opf` on a 0.34 deck whose own keys fail the schema (`design.contentDirection` or `design.chartPrimary` on the deck or a slide, a cell key such as `top:start`), and a removed layout (`auto`, `flow`, `vertical-flow`, `agenda-split`) or a stale embedded copy draws without its layout until it is fixed. A host that stores decks repairs each one when it loads it, before it draws it, not only before it saves: `fix(deck, { catalogs })` and draw `result.document`.

**What a safe fix promises.** `fix()` and `opf fix` apply a fix only when it is marked `safe` and is a JSON Patch: it loses no content and what it writes is valid. A fix that can change how a slide draws says so with `changesDrawing: true` on the finding's fix and on `FixResult.applied[]` (`opf fix`: `fix.applied[].changesDrawing`, the count in `fix.changesDrawing`, and "(changes the drawing)" in `--format text`); the fixed deck keeps every word but does not keep the 0.34.2 drawing. A host that tells its users the repair keeps how the deck looks says so only when no applied fix has `changesDrawing`, and lists the slides of those that do. The marks: `rename-layout` from `agenda-split` and `flow` (also on a stale embedded copy), `remove:contentDirection`, `remove:chartPrimary` outside a layout record, and `remove:listColumns` other than `"auto"` on a list region. Every other safe fix keeps the drawing. Drawn for a deck each with 0.34.2 and fixed with 0.35, the same: `remove-layout-auto`, `rename-layout` from `vertical-flow`, `use-current-record`, `rename-region`, `cells-to-blocks`, `use-max-1`, `use-arrangement`, `use-inverted-pyramid`, `use-pyramid` and `rename-arrangement`. A new name for the same value: `icon-renamed`, `change-to:start` and `change-to:end` on a stale copy, `convert-to-string` and `wrap-in-list` (a deck 0.34.2 already refused). What 0.35 draws differently for every deck (a `steps` region's short list as Basic Process, long lists in columns) changes with or without a fix and is in the rows above. A `focus` fix (`focus-language`, `focus-alt`) names a field a person writes: it is never applied and never counted as a safe fix, whatever its `safe`.

**The default scope.** `fix()` and `opf fix` apply by default only the safe fixes of the checks that repair the document, `FIX_REPAIR_CATEGORIES`: `format`, `references`, `policy` and `layout` (`opf/region-unknown`'s `rename-region`). The audits (`accessibility`, `content` and any other producer's category) are reported with their fixes but applied only with `fix(deck, { audits: true })` or `opf fix --audits`; `opf fix` lists them in `fix.audits` otherwise. Today the one safe audit fix is `use-canonical-tag` (a language tag in the wrong case). `use-readable-color` (`opf/text-contrast`) is no longer safe: it replaced a color the author wrote with one the check chose, so it changed how the slide looks, and other repairs keep the author's intent (a darker shade, another background, removing the override). `fix` never applies it; the editor's Review panel shows it with its "changes how the slide looks" warning, as it now shows a safe fix with `changesDrawing`. New core exports: `FIX_REPAIR_CATEGORIES` and `isSafePatch(fix)`, the test `fix` uses (safe and a patch with operations), for a host that counts the fixes it will apply.

**Empty design objects.** `remove:contentDirection` and `remove:chartPrimary` remove the `design` object (of a slide, the deck, a theme or a layout record) when the key was all it held, and `fix` removes a `design` that two of them emptied in one round, so a fixed deck has no `"design": {}`. An empty `design` the author wrote is kept.

**Decks with a layout and cells.** A host that writes 0.34 cell keys (`start`, `top:start`, ...) writes blocks that name the cells instead: `"blocks": [{ "region": "start", ... }]`, on a slide without `layout`. For decks it stored, `fix(deck)` (or `opf fix`) migrates every slide in cells; a slide that also names a layout is reported in `FixResult.layoutWithCells` (`opf fix`: `fix.layoutWithCells`), one entry per slide: `{ slide, layout, rewritten: true, kept }` when the fix removed the layout and kept on the slide what it gave (`kept` names the keys written, such as `design.variant`), which draws exactly as 0.34 drew it, or `{ slide, layout, rewritten: false, reason }` when it left the slide because no slide without that layout draws the same. A left slide stays invalid (its cells draw nothing) until someone applies one of its two fixes: show the reason and offer `cells-to-blocks` (remove the layout) or `cells-to-layout-blocks` (keep it).
