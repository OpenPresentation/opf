# Updating from 0.34 to 0.35

0.35 changes little that a deck or a host has to act on. For a deck, run `opf fix deck.opf.json -i`, then validate (`opf validate deck.opf.json --fail-on warning`). `opf fix` brings the deck to the 0.35 form and the 0.35 engine draws it, so a slide may look different than it did in 0.34. Each deck change below is reported, and most come with a fix marked safe (it loses no content and writes valid OPF): `opf fix` applies those, in the deck and in its own layout records, including the stale copies of built-in layouts in a self-contained deck ([below](#self-contained-decks-embedded-copies-of-built-in-layouts)), and lists each one, marking those that can change how a slide draws (`changesDrawing`, below: `rename-layout` from `agenda-split` or `flow`, `use-current-record`, `cells-to-layout-blocks`, `remove:contentDirection`, `remove:chartPrimary` and some `remove:listColumns`). By default it applies only the fixes of the checks that repair the document; an audit's fix (accessibility, content) waits for `--audits`, and a fix that restyles content, such as a new text color, is not safe at all. It validates again after each round of fixes, since an error in the deck's own keys stops the accessibility, layout and content checks, so findings such as `opf/region-unknown` appear only once it is fixed. A fix that needs a choice (such as `role: "secondary"`) is never applied: `opf validate` reports it with its fixes, and `opf fix` lists it in `fix.unsafe`. From code, core's `fix(deck)` does the same.

### Self-contained decks (embedded copies of built-in layouts)

`opf embed` (core `embed()`) copies every built-in layout a deck uses into `catalogs.default.layouts`, as the release that ran it published the record. 0.35 changed the keys of those records (`flow: "none"`, `listColumns`, `sequence`, `pyramidDirection`, the `flow` arrangement, `design.contentDirection`) and an earlier copy can also carry 0.34's `left` and `right` alignments, so such a copy fails the 0.35 layout schema: every deck made self-contained before 0.35 (pptx.gallery's how-to decks, pptx.dev's saved and starter decks, openpresentation.org's tutorials) is invalid, and `opf convert` stops with `invalid-document`.

| What | In 0.35 |
| --- | --- |
| The fix | `opf fix deck.opf.json -i` applies the fix of each stale copy (`use-current-record`, or `rename-layout` for a layout 0.35 removed) with the deck's other safe fixes; or `opf embed deck.opf.json -i`, which replaces the copies alone. `catalogs.default` mirrors the built-in records, so each stale copy takes the current record, whatever release wrote it and whether it was edited (keep a customized layout in `catalogs.custom`, which is never replaced), and each pin of its slides takes the region's 0.35 name; a copy of a layout 0.35 removed moves its slides to the replacement and is dropped (as `rename-layout` does). `opf embed` writes the deck and lists the copies in the report's `embed.refreshed` (`how` `current` or `renamed`, `changesDrawing` when the record changed). The 0.35 engine draws the slides, which may look different. Then validate again. It still refuses a deck with other invalid content, listing it; fix that and run it again. |
| `opf validate` | Each error in the copy says what it is. Its message starts with it ("catalogs.default.layouts.cover is a copy of the built-in layout 'cover' from before OPF 0.35: must be equal to one of the allowed values"), and its help says it in full ("catalogs.default.layouts.cover is a copy of the built-in layout 'cover' from before OPF 0.35; 0.35 changed the keys of the built-in records, so the copy fails the 0.35 layout schema."), then how to fix it and what replaced the key. Its one fix is `use-current-record` (or `rename-layout`), safe and marked `changesDrawing`: it replaces the copy with the current record and renames the pins of its slides. Without a registered catalog that publishes the record, the copy is checked as any record, with the fix of each key. |
| A slide on a stale copy | `opf/unresolved-reference` says "Layout 'cover' is embedded in catalogs.default, but the record fails the layout schema: see the opf/catalog-record findings at /catalogs/default/layouts/cover." with the same cause and fix. It said the layout was not embedded. A record of the deck's own (`catalogs.custom`) gets the same message and its keys' fixes; `opf embed` does not change it, `opf fix -i` applies the safe ones. |
| `opf convert`, `opf paginate` and the other writing commands | Still refuse the deck (`opf fix -i` first). When findings carry a safe fix, their error names it ("2 findings carry a safe fix: `opf fix <deck> -i` applies them, then validate again."), and it ends "The deck embeds copies of built-in layouts from before OPF 0.35 (cover): `opf embed <deck> -i` replaces each one with the current record; validate again after it." |
| `--check` | `opf embed deck.opf.json --check` exits 1 when a copy would be refreshed. |

## Custom layout records

`opf fix deck.opf.json -i` applies the safe fixes below to the deck's own records (`catalogs.custom`, which `opf embed` does not change) and leaves the others for you, listed in `fix.unsafe`.

| In 0.34 | In 0.35 |
| --- | --- |
| A region with `"role": "secondary"` (bound after `primary`, before `supporting`) | Write `"role": "supporting"` (or `"primary"`, or leave `role` out for the default `primary`). `role` is `primary`, `media` or `supporting`; `secondary` fails the layout schema: `opf validate` reports `opf/catalog-record` at the region's `role`, says it was removed and offers `change-to:supporting` and `change-to:primary` (neither marked safe: which one keeps the binding depends on the record, so `opf fix` leaves it), and until it is fixed the engines read that region as `primary`. The gallery `dashboard` layout's `kpis` region is `supporting` now and draws as before. |
| A region with `"sequence": "steps"` or `"sequence": "numbered"` (step badges) | `"arrangement": "steps"` or `"arrangement": "numbered"` (safe fix `use-arrangement`). A region has one `arrangement`: a sequence (`steps`, `numbered`) or a diagram, never both. |
| A region with `"arrangement": "flow"` or `"arrangement": "vertical-flow"` | `"arrangement": "process"` or `"arrangement": "vertical-process"` (safe fix `rename-arrangement`), PowerPoint's names (Basic Process and Vertical Process). The gallery's `flow` layout is gone (its `process` layout draws a short list as Basic Process) and `vertical-flow` is `vertical-process` (Decks, above). |
| A region with `"arrangement": "steps"`: its lone list of 3 to 6 entries of one or two words drew as a row of chips joined by arrows | Its lone list of 2 to 8 entries of one level, each of one or two words and at most 24 characters, without numbering, descriptions or icons, draws as Basic Process in the region's whole cell where Basic Process holds every entry at the size its steps would have or larger; otherwise the list draws as steps. | How validation reports the old keys and values | `sequence` and `pyramidDirection` fail the layout schema as unknown keys and `flow` and `vertical-flow` as unknown values: `opf validate` reports `opf/catalog-record` (error) at the region's `sequence` or `pyramidDirection` key, or at its `arrangement`, says what replaced it and offers the safe fix: `use-arrangement` (`sequence` becomes `arrangement`, for a region without one), `use-inverted-pyramid` (`pyramidDirection: "down"` on a pyramid), `use-pyramid` (`"up"`: the key is dropped) and `rename-arrangement` (`flow` to `process`, `vertical-flow` to `vertical-process`); `opf fix -i` applies them. | A region with `"max": 1` and a flowing `flow` (`auto`, `grid`, `column`) | It is a single-block region now (above): it is no longer the default overflow region, and blocks no region had room for may join it instead of being drawn beyond its `max` with `opf/layout-unplaced`. | `design.chartPrimary` in a layout record's `design` | Delete it (it never applied on a slide with a layout); safe fix `remove:chartPrimary`. |

| `design.contentDirection` in a theme record's `design` | Delete it; the theme's other design keys are unchanged. Safe fix `remove:contentDirection`. |
| An id `auto` was refused for a layout record | Allowed: `auto` is an ordinary id. |
| A region with `"listColumns": "auto"` or `1` | Delete it: a list of more than 6 entries flows into columns by default in a region without an `arrangement` (or with `numbered`), when the columns set it at least as large as one column (a region whose first accepted kind is `list` keeps the rule `"auto"` had); a region with a diagram or `steps` keeps one column. To keep a list in one column, write `"columns": 1` on the list. `listColumns` fails the layout schema: `opf validate` reports `opf/catalog-record` at the key, says what replaced it and offers the safe fix `remove:listColumns` (`opf fix -i` applies it), marked `changesDrawing` unless the value is `"auto"` on a region made for a list (`list` first in `accepts`, no arrangement or `numbered`), whose rule 0.35 keeps; an engine handed the record directly ignores it. ## Hosts and scripts

**Repair before drawing.** The 0.35 renderer's `toSvg` throws `invalid-opf` on a 0.34 deck whose own keys fail the schema (`design.contentDirection` or `design.chartPrimary` on the deck or a slide, a cell key such as `top:start`), and a removed layout (`auto`, `flow`, `vertical-flow`, `agenda-split`) or a stale embedded copy draws without its layout until it is fixed. A host that stores decks repairs each one when it loads it, before it draws it, not only before it saves: `fix(deck, { catalogs })` and draw `result.document`.

**What a safe fix promises.** `fix()` and `opf fix` bring a deck to the 0.35 form, and the 0.35 engine draws it. They apply a fix only when it is marked `safe` and is a JSON Patch: it loses no content and what it writes is valid. A fix that can change how a slide draws says so with `changesDrawing: true` on the finding's fix and on `FixResult.applied[]` (`opf fix`: `fix.applied[].changesDrawing`, the count in `fix.changesDrawing`, and "(changes the drawing)" in `--format text`); the fixed deck keeps every word and draws in the 0.35 form. A host that tells its users how the repair affects their deck lists the slides of the fixes with `changesDrawing`. The marks: `rename-layout` from `agenda-split` and `flow` and on a stale embedded copy, `use-current-record`, `cells-to-layout-blocks`, `remove:contentDirection`, `remove:chartPrimary` outside a layout record, and `remove:listColumns` other than `"auto"` on a list region. The other safe fixes write a new name or form for the same value: `remove-layout-auto`, `rename-layout` from `vertical-flow`, `rename-region`, `cells-to-blocks`, `use-max-1`, `use-arrangement`, `use-inverted-pyramid`, `use-pyramid`, `rename-arrangement`, `icon-renamed`, `change-to:start` and `change-to:end` in a record, `convert-to-string` and `wrap-in-list` (a deck 0.34.2 already refused). What 0.35 draws differently for every deck (a `steps` region's short list as Basic Process, long lists in columns) changes with or without a fix and is in the rows above. A `focus` fix (`focus-language`, `focus-alt`) names a field a person writes: it is never applied and never counted as a safe fix, whatever its `safe`.

**The default scope.** `fix()` and `opf fix` apply by default only the safe fixes of the checks that repair the document, `FIX_REPAIR_CATEGORIES`: `format`, `references`, `policy` and `layout` (`opf/region-unknown`'s `rename-region`). The audits (`accessibility`, `content` and any other producer's category) are reported with their fixes but applied only with `fix(deck, { audits: true })` or `opf fix --audits`; `opf fix` lists them in `fix.audits` otherwise. Today the one safe audit fix is `use-canonical-tag` (a language tag in the wrong case). `use-readable-color` (`opf/text-contrast`) is no longer safe: it replaced a color the author wrote with one the check chose, so it changed how the slide looks, and other repairs keep the author's intent (a darker shade, another background, removing the override). `fix` never applies it; the editor's Review panel shows it with its "changes how the slide looks" warning, as it now shows a safe fix with `changesDrawing`. New core exports: `FIX_REPAIR_CATEGORIES` and `isSafePatch(fix)`, the test `fix` uses (safe and a patch with operations), for a host that counts the fixes it will apply.

**Empty design objects.** `remove:contentDirection` and `remove:chartPrimary` remove the `design` object (of a slide, the deck, a theme or a layout record) when the key was all it held, and `fix` removes a `design` that two of them emptied in one round, so a fixed deck has no `"design": {}`. An empty `design` the author wrote is kept.

**Decks with cells.** A host that writes 0.34 cell keys (`start`, `top:start`, ...) writes blocks that name the cells instead: `"blocks": [{ "region": "start", ... }]`, on a slide without `layout`. For decks it stored, `fix(deck)` (or `opf fix`) migrates every slide in cells: a slide without a layout with `cells-to-blocks`, and a slide with a layout with `cells-to-layout-blocks`, which keeps the layout and moves the content into blocks that bind to its regions by kind (marked `changesDrawing`).
