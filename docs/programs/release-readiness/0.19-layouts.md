# OPF 0.19: intent layouts and grid templates

Approved by the owner on 2026-10-10 ([opf#507](https://github.com/OpenPresentation/opf/issues/507)). 0.19 replaces the 278
layout records of the default catalog with 28 layouts named by intent, all written in one grid-template syntax that a deck or
a catalog can also use for its own layouts. It is one breaking lockstep 0.x minor (core, renderer, PPTX, editor and CLI) with
a major release of the catalog, `@openpresentation/gallery` 2.0.0, and it ships without aliases or shims, as the pre-v1 rule
allows. It lands in the same train as RR-77 and RR-78 B. Burndown items RR-79 to RR-84 implement it, one per phase of
section 11.

Every decision below that the owner did not state is an agent decision, marked *(vetoable)* where changing it is cheap now
and expensive after the release.

## 1. Two layers, one format

- **Built-in layouts.** 28 layouts named by intent (`pillars`, `chart-beside`, `agenda`, ...). Content flows inside them: no
  layout fixes a block count, so adding a fourth point to a `pillars` slide reflows it instead of asking for another layout.
- **Grid templates.** The syntax every layout is written in, the built-ins included. A custom layout is one more template,
  embedded in a deck (`catalogs.custom.layouts`) or shipped in a catalog. Nothing distinguishes a built-in from a custom
  layout except where its record lives.

Today's 278 records are about 15 content shapes multiplied by block count (1 to 6), boxed or not, vertical or not, title
position, crop or fit and item images. The count disappears into flow (section 4) and every other axis already exists as a
design key (section 5).

## 2. A layout is regions

A layout record (`https://openpresentation.org/schema/opf-layout/v2`; `CATALOG_SCHEMA` becomes 2) has these fields:

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | kebab-case string | The record's id. Required in a published file; the key in an embedded copy. |
| `name` | string | Shown in layout pickers and as the PowerPoint layout name. |
| `summary` | string | One line: when to reach for it. |
| `description`, `tags`, `preview` | as in v1 | Unchanged. |
| `areas` | 1 to 12 strings | The grid, in the notation of CSS `grid-template-areas`: each string is a row, each word a cell, and a name repeated over adjacent cells spans them. `.` is an empty cell. |
| `columns` | numbers | Relative column widths, one per cell of a row. Omitted: all 1. |
| `rows` | numbers or `"auto"` | Relative row heights, one per string. `auto` is the height the row's content needs. Omitted: all 1. |
| `regions` | object | One entry per body area name, keyed by it (below). |
| `overflowRegion` | region name | Where content no region accepts goes (section 3). Omitted: the first `primary` region whose flow is not `none`. |
| `design` | DesignHints | The layout's design defaults (section 5). |
| `composition` | object | Only `gap`, `padding`, `minFontSize` and `overflow`, with their 0.18 meaning. |

Removed from the record, with no alias: `placeholders`, placeholder groups (FA-26), the image placeholder's `placement`, and
`composition.mode`, `columns` and `weights`. Areas and regions say all of that.

### The area notation

```
areas: ["title title",          columns:  2          1
        "timeline notes",                +----------------------------------+
        "timeline metrics"]      auto    | title                            |
                                         +----------------------+-----------+
rows: [auto, 1, 1]                 1     | timeline             | notes     |
                                         |                      +-----------+
                                   1     |                      | metrics   |
                                         +----------------------+-----------+
```

`title title` is one area, `title`, spanning both columns. `timeline` appears in two rows of the first column, so it is one
area spanning both rows. A name's cells must form one filled rectangle.

- Words are `[a-z][a-z0-9-]*` or `.`, separated by one or more spaces. Every string has the same number of words.
- `title` and `subtitle` are heading areas. `title` holds the slide's heading group (tag, title and subtitle, stacked as
  today); a `subtitle` area takes the subtitle out of it. They have no `regions` entry. A `subtitle` area needs a `title`
  area. A layout with no `title` area gets an implicit `auto` row on top for a slide that has headings.
- Every other name is a body region and needs an entry in `regions`. Region names may not be `title`, `subtitle`, `tag`,
  `auto` or one of the six promoted-region words (`left`, `center`, `right`, `top`, `middle`, `bottom`), so `region=` in the
  Markdown dialect stays unambiguous (section 7).
- `columns` are numbers only. `auto` is a row size: an `auto` column would need the text's width before its wrapping, and
  every use so far (heading rows, notes rows, caption rows) is a row *(vetoable)*.

### Regions

| Field | Values | Default | Meaning |
| --- | --- | --- | --- |
| `accepts` | content kinds, at least one | required | Kinds the region takes: `text`, `list`, `image`, `video`, `chart`, `table`, `code`, `metric`, `quote`, `timeline`, and `group` for a content group of any content. A group is also accepted where every one of its leaf kinds is. |
| `role` | `primary`, `secondary`, `media`, `supporting` | `primary` | Which content the region wants first (section 3). |
| `flow` | `none`, `grid`, `column`, `auto` | `auto` | How several blocks share the region (section 4). |
| `max` | 1 to 12 | 1 for `none`, else 6 | Blocks the region holds on one slide. `none` requires 1. |
| `bleed` | boolean | `false` | The region's outer edges that lie on the content box's edge extend to the slide edge, as a placed image does today. A bled region is never drawn as a card. |
| `listColumns` | `"auto"`, `1` | `1` | A lone list in the region flows into up to three columns before it shrinks (section 4). |
| `anchor` | `top`, `middle`, `bottom` | `top` | Vertical position of the region's content when it is shorter than the region. |
| `empty` | `collapse`, `keep` | `collapse` | What an empty region does (section 3). |

### Validation

The schema checks types, enums and ranges (an unknown kind in `accepts` is `opf/catalog-record`, as any schema error of an
embedded record). `validate` adds:

| Code | Severity | Raised for |
| --- | --- | --- |
| `opf/layout-template` | error | Ragged rows; a name whose cells are not one filled rectangle; `columns` or `rows` of the wrong length; a grid over 12 x 12; a word that is not a name or `.`. |
| `opf/layout-region` | error | A body area with no region; a region with no area; a reserved region name; a `subtitle` area without `title`; `flow: none` with `max` other than 1; an `overflowRegion` that is not a region. |

Region names are the keys of `regions`, so they are unique; the YAML and Markdown readers already reject duplicate keys.
`composeSlide` refuses a record with either finding, as it refuses a fourth placeholder-group level today.

## 3. Content binding

Slide content stays flat: `blocks`, or a root payload (one block). Nothing in a slide names a grid position unless the
author pins it. The engine binds blocks to regions; `bindRegions(slide, record)` (core, pure) returns the binding and its
findings, and `composeSlide` uses it.

**Inputs.** The slide's root nodes in source order, without headings and without placed images (an image block with
`placement` takes its band as today and never occupies a region). A content group is one node of kind `group`. The record's
regions in reading order: by the top-left cell of each area, row by row, then cell by cell. A right-to-left deck mirrors the
drawing, not this order.

**Step 1, pins.** A block with `region: "<name>"` goes to that region, in source order, when the region exists, accepts the
block's kind and has room (fewer than `max` blocks). Otherwise the pin is ignored with a warning and the block joins step 2:

| Code | When |
| --- | --- |
| `opf/region-unknown` | The layout has no region of that name. |
| `opf/region-kind` | The region does not accept the block's kind. |
| `opf/region-full` | The region already holds `max` blocks. |

**Step 2, everything else, in source order.** For each block, the candidates are the regions that accept its kind and have
room. The block goes to the candidate with the smallest key:

1. **Role rank**, which depends on the kind:

   | Block kind | `media` | `primary` | `secondary` | `supporting` |
   | --- | --- | --- | --- | --- |
   | `image`, `video` | 0 | 1 | 2 | 3 |
   | every other kind, `group` included | 3 | 0 | 1 | 2 |

2. **Reading order** of the region.

So a primary region fills before a supporting one, a picture prefers a media region, and of two equal regions the first in
reading order fills first. A supporting region receives content only when no primary or secondary region that accepts the
kind has room, or by a pin. Within a region, blocks keep source order.

**Step 3, content no region takes.** A block with no candidate goes to the overflow region (`overflowRegion`, or the first
`primary` region whose flow is not `none`), whatever its `accepts`, while it has room. A block that still has no place is
never dropped: it is drawn in the overflow region beyond `max` (the flow grows by its rule in section 4), and `paginate`
moves it to a continuation slide instead. Each such block is one warning, `opf/layout-unplaced`, naming the block's path and
the region it was drawn in. A layout with no flowing primary region and no `overflowRegion` draws it in an implicit `auto`
row below the grid.

**Empty regions.** A region that receives no block collapses (unless `empty: keep`): its cells join a neighbouring region
that shares the full length of one of its edges and is not itself empty. The neighbours are tried in the order start side,
end side, below, above, and a body region is preferred to a heading area in that order. With no such neighbour the space
stays blank. An `auto` row whose areas are all empty has zero height and its gap is removed. A heading area is empty when the
slide has no tag, title or subtitle, and then collapses the same way. Collapsing is computed per slide and never changes the record. `geometry.regions` (it
replaces `geometry.slots`) lists every region with its name, box, flow, accepted kinds, the content paths bound to it and
`collapsed: true` for an empty one, so editors can show drop targets.

**Headings.** The heading group goes to the `title` area (and the subtitle to a `subtitle` area). Headings are centred
vertically in their area unless every row the area spans is `auto`, so `cover` and `section` centre their title (the 0.18
cover rule, now read from the template) while content layouts keep it at the top.

**Promoted regions.** A slide that uses promoted regions (`left`, `top:left`, ...) keeps them in 0.19: its body is composed
as today inside the content box below the `title` area, and the layout's body regions are not used. See question 6.

## 4. Flow and overflow

### Flows

| `flow` | Blocks are arranged |
| --- | --- |
| `none` | One block fills the region. |
| `grid` | By count, in a landscape region: 1 fills it; 2 side by side; 3 in a row; 4 as 2 x 2; 5 as 3 + 2; 6 as 3 x 2; 7 to 12 in four columns, `ceil(n / 4)` rows. In a portrait region (taller than wide) rows and columns swap (2 stacked, 3 stacked, 4 as 2 x 2, 5 as 2 + 2 + 1, 6 as 2 x 3, 7 to 12 in three rows). A short last row keeps the column width of the full rows and is centred *(vetoable)*. |
| `column` | Stacked top to bottom, equal heights. |
| `auto` | `grid` when every block is short, `column` when any block is long. |

Adding or removing a block reflows the region by the same rule; nothing else on the slide moves except through collapse.

**Long.** A block is long when, set in the cell the `grid` arrangement would give it at the starting body size (25 reference
pixels at a 720-pixel short edge, the size `fontReduction` measures from), it needs more than **6 lines**. Lines count after
wrapping: a list counts every line of every item and description, a quote its body lines, a table its rows (header included),
code its source lines (long above 12). Images, video, charts, metrics and timelines are never long. The measurement is
core's deterministic estimate (`textMeasurement: "estimated"`), never a host font provider, so `auto` picks the same
arrangement in the preview, in PowerPoint and on every OS *(vetoable: the threshold is tuned against the gallery fixtures
before release)*. As a rule of thumb, a third of a 16:9 slide holds about 30 characters a line, so a block is long above
about 180 characters there.

**Overrides.** The resolved `design.contentDirection` (section 5) turns every flowing region of the slide into one row
(`horizontal`) or one column (`vertical`). A slide's own `composition.mode`, `columns` and `weights` act on the slide's first
primary flowing region and rank above `contentDirection`: `row`, `column`, `grid` (with `columns`) and `auto` (the 0.18
scored grid search). `gap`, `padding`, `minFontSize` and `overflow` keep their 0.18 meaning for the whole slide.

### Tracks

The content box is the canvas minus padding, header and footer bands, the footnote area and placed-image bands. An `auto`
row is as tall as its content needs at the starting size (headings as they reserve space today, a flowing region at its
area's width), at most half the content box; areas that span several rows do not size an `auto` row. The numeric rows share
the rest in proportion; columns share the width in proportion. Tracks are separated by `gap`. Collapsed rows take zero height.

### One long list

A lone list block in a region with `listColumns: "auto"` (the `list`, `agenda` and `faq` layouts), or any list payload with
the new field `columns: "auto"`, is laid out in 1, 2 then 3 equal columns at the starting size, and the first count at which
it fits is used, as long as a column stays at least a quarter of the slide wide. Column breaks fall between items, never
inside one, a nested item stays with its parent, and the breaks are chosen so the columns are as even as possible. Numbering
continues across columns and reading order runs column by column. When the largest allowed count does not fit, the text shrinks towards
`minFontSize` as any text does, and then overflows. `columns: 1`, `2` or `3` on the payload fixes the count. This is the
most common reason `list-2x` is used today.

### Pagination

`paginate` (and `opf paginate`, and the editor's **Split overflow**) continues on a new slide with the **same layout** and
design, and never drops content:

1. Blocks beyond a region's `max` move to the continuation, in source order.
2. A region whose text does not fit at `minFontSize` splits as today: lists between items (after `listColumns` has been
   tried), tables between rows with their labels repeated, text at sentence and then word boundaries, code without rewriting
   its source.
3. Moved blocks carry a `region` pin to the region they came from, so they land in the same place. Headings repeat; regions
   with nothing on a page collapse.
4. An atomic block that does not fit an otherwise empty page in its region is `OPFPaginationError`, with no partial output.

Pagination stays an authoring operation; rendering without it draws overflow with its diagnostics, as today.

### No layout

A slide with no `layout`, or `layout: "auto"`, composes automatically exactly as in 0.18 (the scored grid search,
`chartPrimary`, the cover rule). `auto` is reserved: no catalog may define a layout of that id, and `opf format` drops
`layout: "auto"`.

## 5. Variants are design settings

The axes the 278 ids encoded are design keys, set on the deck or the theme and overridden per slide. They are not layout ids.

| Key | Values | Was the id part | In 0.19 |
| --- | --- | --- | --- |
| `contentBox` | boolean | `-box` | Each body block drawn as a card (unchanged). |
| `contentDirection` | `horizontal`, `vertical` | `-vertical` | Every flowing region becomes one row or one column (section 4). Unset: each region's own flow. |
| `titleAlignment` | `left`, `center`, `right` | `-title-center`, `-title-left` | Unchanged. |
| `contentAlignment` | `left`, `center`, `right` | `-center`, `-left` | Unchanged. |
| `listBullet` | `character`, `image` | `-itemimage` | Unchanged: `image` draws the organization's icon as the bullet. |
| `imageFit` | `cover`, `contain`, `stretch` | `-crop`, `-fit` | Unchanged. |

The approved list names `itemImage` beside `listBullet`. The `-itemimage` records set only `listBullet: "image"`, so 0.19
adds no `itemImage` key; see question 4. `chartPrimary` keeps its 0.18 meaning on automatic slides and is not used on a
layout slide, where `chart-beside` says the same thing.

**Precedence**, per key: the slide's `design`, the deck's `design`, the **theme record** (new: a theme may carry these six
keys, so "our decks are boxed" is set once), the layout record's `design`, then the engine default. 0.18 had no theme level
for these keys.

## 6. The built-in set

28 layouts in six groups. Every one has a title area, so a picker can preview it with sample content, and every body region
collapses when empty, so a layout with an optional picture or note does not need a second id.

| Group | Layouts |
| --- | --- |
| Openers and closers | `cover`, `section`, `agenda`, `statement`, `closing` |
| Text | `text`, `list`, `quote`, `two-column` |
| Groups of items | `pillars`, `comparison`, `process`, `timeline`, `faq` |
| Numbers | `metrics`, `scorecard` |
| Visuals | `image`, `image-beside`, `gallery`, `chart`, `chart-beside`, `table`, `table-beside`, `code` |
| Mixed | `hero`, `dashboard`, `team`, `logos` |

**Against the 278.** Every current record maps to one of these with design settings (section 9); every one of the 28 is the
target of at least one record. Records per target: `list` 84, `text` 45, `gallery` 41, `metrics` 25, `chart` 18, `cover` 11,
`image` 5, `pillars` 5, `chart-beside` 4, `image-beside` 4, `timeline` 4, `comparison` 3, `quote` 3, `table` 3, two each for
`agenda`, `closing`, `hero`, `process`, `scorecard`, `section`, `statement` and `team`, one each for `code`, `dashboard`,
`faq`, `logos`, `table-beside` and `two-column`, and `blank` becomes no layout. The draft list is kept as it was. Considered
and left out:

- **`blank`**: a record with no placeholders composes exactly like no layout, so it maps to `auto`.
- **`matrix`** (SWOT, quadrant): four blocks in `pillars` are already 2 x 2; the axis labels a matrix needs are not in any
  record today.
- **`diagram`**: 13 records are diagrams by name (hub and spoke, Venn, wheel, decision tree, swimlane, ecosystem map, org
  chart, logic tree, ...) but hold an image, a text or a chart. Without a diagram content kind a `diagram` layout would be one
  of those under another name; they map by what they hold, to `gallery`, `text`, `chart`, `process` or `hero` (question 13).
- **`figure`** (one framed picture under a title): `gallery` with one picture.
- **`business-model-canvas`**: a fixed nine-box structure is what custom templates are for; it maps to `pillars` with its
  groups kept, and becomes a custom-template example in the docs (question 15).

Some layouts gained an optional supporting row that the draft did not spell out: a `note` under `metrics`, `chart` and
`table`, `notes` under `timeline`, a `verdict` under `comparison`. Each collapses when empty and takes text that would
otherwise have no region.

In the sketches, `####` is a bled region and the body shows a typical number of blocks.

## 7. Custom layouts

A custom layout is a record of the same schema. It is embedded under `catalogs.custom.layouts` (or a named catalog group)
and referenced by id like any layout; a catalog package ships it the same way the gallery ships the built-ins. The example
below, `roadmap-split`, puts a timeline on the left two thirds and stacks notes over metrics on the right
(the [area notation](#the-area-notation) diagram above is this layout). The three forms are the same deck.

**JSON** (`roadmap.opf.json`):

```json
{
  "name": "Roadmap review",
  "catalogs": {
    "custom": {
      "layouts": {
        "roadmap-split": {
          "name": "Roadmap split",
          "summary": "A roadmap on the left, with notes over metrics beside it.",
          "areas": ["title title", "timeline notes", "timeline metrics"],
          "columns": [2, 1],
          "rows": ["auto", 1, 1],
          "regions": {
            "timeline": { "accepts": ["timeline"], "role": "primary", "flow": "none" },
            "notes": { "accepts": ["text", "list"], "role": "secondary", "flow": "column" },
            "metrics": { "accepts": ["metric", "text"], "role": "supporting", "flow": "grid" }
          }
        }
      }
    }
  },
  "slides": [
    {
      "layout": "roadmap-split",
      "title": "2027 roadmap",
      "blocks": [
        { "timeline": { "events": [{ "when": "Q1", "what": "Pilot" }, { "when": "Q2", "what": "Launch" }] } },
        { "metric": { "value": 12, "label": "Pilot customers" } },
        { "metric": { "value": "94%", "label": "Retention" } },
        { "items": ["Hiring two engineers", "Security review in Q1"] },
        { "region": "metrics", "text": "Targets agreed with finance." }
      ]
    }
  ]
}
```

**YAML** (`roadmap.opf.yaml`):

```yaml
name: Roadmap review
catalogs:
  custom:
    layouts:
      roadmap-split:
        name: Roadmap split
        summary: A roadmap on the left, with notes over metrics beside it.
        areas: ["title title", "timeline notes", "timeline metrics"]
        columns: [2, 1]
        rows: [auto, 1, 1]
        regions:
          timeline: { accepts: [timeline], role: primary, flow: none }
          notes: { accepts: [text, list], role: secondary, flow: column }
          metrics: { accepts: [metric, text], role: supporting, flow: grid }
slides:
  - layout: roadmap-split
    title: 2027 roadmap
    blocks:
      - timeline:
          events:
            - { when: Q1, what: Pilot }
            - { when: Q2, what: Launch }
      - metric: { value: 12, label: Pilot customers }
      - metric: { value: 94%, label: Retention }
      - items: [Hiring two engineers, Security review in Q1]
      - region: metrics
        text: Targets agreed with finance.
```

**Markdown** (`roadmap.opf.md`): the layout is front matter, the slide names it in its options comment, and a block comment
pins the last block. The dialect's `region=` option already moves a block into a promoted region; a value that is not one of
the promoted-region keys (which region names cannot be, section 2) is the block's `region` pin.

````markdown
---
name: Roadmap review
catalogs:
  custom:
    layouts:
      roadmap-split:
        name: Roadmap split
        summary: A roadmap on the left, with notes over metrics beside it.
        areas: ["title title", "timeline notes", "timeline metrics"]
        columns: [2, 1]
        rows: [auto, 1, 1]
        regions:
          timeline: { accepts: [timeline], role: primary, flow: none }
          notes: { accepts: [text, list], role: secondary, flow: column }
          metrics: { accepts: [metric, text], role: supporting, flow: grid }
---

<!-- slide: layout=roadmap-split -->
# 2027 roadmap

```timeline
Q1 — Pilot
Q2 — Launch
```

```metric
value: 12
label: Pilot customers
```

```metric
value: "94%"
label: Retention
```

- Hiring two engineers
- Security review in Q1

<!-- block: region=metrics -->
Targets agreed with finance.
````

**How it binds.** Step 1 puts the pinned text in `metrics`, which accepts text. Step 2 takes the rest in source order: the
timeline goes to `timeline`, the only region that accepts it; the two metrics go to `metrics`, the only one that accepts
metrics; the list goes to `notes`, the only one that accepts lists. Without its pin the text would have gone to `notes` too:
both `notes` and `metrics` accept text, and `notes` is `secondary`, which ranks before `supporting`. `metrics` holds three
blocks, so its grid draws them in a row; with two metrics and no text, `notes` and `metrics` would still split the right
column, and with no notes at all, `notes` collapses into `metrics` below it.

**Records written in 0.18.** `opf convert --migrate` rewrites an embedded v1 record (`placeholders` and `composition`) into a
template: headings become a `title` row, a flat row, column or grid of placeholders becomes one area per placeholder with the
`weights` as track sizes, a record with no mode becomes one `auto` region accepting the union of its kinds, a placeholder
group becomes one region accepting its leaf kinds (`column` flow for a column group, `grid` otherwise), and an image
placeholder with a `placement` becomes a bled region on that edge. Region names are the kind, numbered when repeated
(`chart`, `text-2`). Each converted record is reported (`layout-converted`, info), and slides get `region` pins wherever the
new binding would place a block differently from the 0.18 leaf order.

## 8. PowerPoint

### Export

- **One slideLayout per OPF layout.** Under each slide master (one per theme, as today), every built-in layout of the
  registered catalog and every custom layout the deck embeds becomes a `p:sldLayout` named by the layout's `name`, so
  **Change Layout** lists the OPF layouts. The layout's `type` is the PowerPoint one where it exists (`cover` is `title`,
  `section` is `secHead`, `text`, `list`, `agenda` and `faq` are `obj`, `two-column` and `comparison` are `twoObj`,
  `image-beside` is `picTx`, `statement` and automatic slides are `titleOnly`), otherwise `cust`. Each carries an
  `OPF_LAYOUT_V1` tag (id, group and a record hash) in its common slide data.
- **A placeholder per area**, at the area's box composed for an empty slide at the deck size (nothing collapses on a
  layout): `title` (`ctrTitle` on `cover` and `section`, with `subTitle` for the subtitle), and per body region `pic` when it
  accepts only pictures, `chart` when only charts, `tbl` when only tables, `media` when only video, and a content placeholder
  (`obj`) otherwise. The placeholder's name is the region name; its `idx` is stable (the region's position in `regions`).
- **Slides** relate to the slideLayout of their OPF layout (automatic slides to `OPF auto`, a `titleOnly` layout).
  - A title that fits one accepted line is the slide's native title placeholder, at the composed box; a longer or rich title
    stays the tagged line shapes of today. This is RR-11's rule for footer placeholders (see question 9).
  - A `none` region holding one picture, chart or table binds that object to the region's placeholder (`p:ph idx`), at the
    composed geometry, so PowerPoint's Change Picture, Reset and Change Layout move it.
  - **A flowing region is one placeholder area on the layout; its blocks are written as editable shapes at the geometry core
    composed**, tagged with their region in `OPF_SLIDE_V1`. The slide does not instantiate the placeholder, so no
    "Click to add text" prompt appears on a filled slide; a new slide added in PowerPoint shows the prompts.
  - A list in columns is one text box per column at core's break points (PowerPoint's own `numCol` would break differently).
- **Furniture** stays as RR-72 left it: parts that are the same on every furniture slide are on the master, RR-11's `ftr`,
  `dt` and `sldNum` placeholders and `p:hf` are on the master and on every OPF layout. Where RR-72 needs a furniture variant
  (a shared part only some slides show, or a hidden footer with `showMasterSp="0"`), it is made per OPF layout that needs it
  (`Pillars (no footer)`), only for the pairs the deck uses. Logos stay on the master.

### Import

- An `OPF_LAYOUT_V1`-tagged slideLayout maps back to its OPF id. When the slide's layout relationship names another OPF
  layout than the stored one (the user ran Change Layout), the relationship wins: `slide.layout` becomes the new id
  (`layout-changed`, info) and the content stays flat blocks that the new layout binds.
- Content in an OPF placeholder imports as a block with a `region` pin when the pin is needed to keep it there; text typed
  into a new slide's placeholders imports the same way.
- A foreign deck's layouts map by type: `title` to `cover`, `secHead` to `section`, `obj` and `tx` to `text`, `twoObj` and
  `twoTxTwoObj` to `two-column`, `picTx` to `image-beside`, `blank` and `titleOnly` to automatic, and `cust` by a
  case-insensitive name match against the built-ins, otherwise automatic. Foreign layouts are not converted into custom
  templates in 0.19 (question 10).

### What is native

| Native in PowerPoint | Not native (drawn by OPF, editable shapes) |
| --- | --- |
| A slideLayout per OPF layout, named, in the master; Change Layout lists them | Flow: PowerPoint never reflows a region; grid, column, `auto` and list columns are computed by core at export |
| A placeholder per area, typed by what the region accepts | Blocks in flowing regions, and text blocks in any region |
| One-line titles in the title placeholder; cover and section subtitles | Multi-line and rich titles (tagged line shapes) |
| A lone picture, chart or table in a `none` region, bound to its placeholder | Collapse of empty regions (each slide's geometry is explicit) |
| RR-72 master furniture, RR-11 footer placeholders and `p:hf` | Bleed (explicit geometry per slide), cards (`contentBox`) |
| Change Layout moves placeholder-bound content; reimport rebinds everything | Change Layout does not move flowing shapes inside PowerPoint |

## 9. Migration from the 278 ids

**Rule.** Every id of the 0.18 default catalog that 0.19 removes maps to one built-in layout and the design settings that
reproduce its variant. The target always accepts every content kind the old record held, so no slide loses a region for its
content. Geometry is not preserved exactly (that is the point of a major release); content, order and intent are.

- **Settings.** For each design key the old record set, the old value is written to the slide's `design` when it differs
  from the new layout's own value (or the engine default when the new layout sets none). A key the old record did not set is
  not written, so the canonical records (`title`, `text-1x`, ...) take the new layout's opinion. `contentDirection` is
  written only when it was `vertical`: the old records wrote `horizontal` on almost every record, including one-region ones,
  and carrying it would turn every `auto` region into a row *(vetoable)*. The records' `composition` (`mode`, `columns`,
  `weights`, `gap` 0.06 on three records and 0.02 on seven, `padding` 0.04 or 0.12 on 17) is not carried; the regions replace it.
- **Hoisting.** After rewriting the slides, a key and value that every slide of the deck received moves to the deck's
  `design`, when the deck does not set that key.
- **Content.** 16 records with placeholder groups (`groups` below) have their slide content wrapped into content groups with
  the group's composition, so the cards stay together (an image with its caption text, a metric with its comment). The six
  title-with-image records (`placement` below) move their image placeholder's placement onto the slide's matching top-level
  image block, exactly reproducing the band. `blank` drops the `layout` field. Wherever the new binding would place a block
  differently from the 0.18 leaf order, the block gets a `region` pin.

**Findings and tools.**

- A slide whose `layout` is a removed id that resolves nowhere raises **`opf/layout-removed`** (error) naming the replacement
  and the settings, with a safe `patch` fix that applies this row. The slide composes automatically meanwhile; engines never
  substitute the replacement, and a strict export fails. A removed id embedded under `catalogs.default` is the same finding
  (the embedded v1 record also fails the v2 schema).
- `opf convert <deck> -i --migrate` (or to another file) applies every fix of the deck and converts embedded v1 records
  (section 7); core exports the same as `migrate(deck)`, returning the deck and the list of changes. The editor offers it as
  one undoable action when it opens a 0.18 deck. There are no aliases: after 0.19 the old ids exist only in this table and in
  core's `spec/reference/layout-migration.json`, which this table is generated from.
- pptx.gallery adds the 278 rows to `data/layout-redirects.json`, so `/layouts/<old-id>` redirects permanently.

**Totals.** 278 rows. 216 rows write design settings and 62 write none. Settings written: `contentAlignment: center` 109,
`titleAlignment: center` 89, `contentBox: true` 77, `contentDirection: vertical` 72, `listBullet: image` 23,
`imageFit: contain` 19, `titleAlignment: left` 5, `contentBox: false` 2, `contentAlignment: left` 1. Content rewrites: 16

## 10. Authoring

- **Where the package lives.** `@openpresentation/gallery` lives in
  [OpenPresentation/gallery](https://github.com/OpenPresentation/gallery): OpenPresentation/gallery#1 moved the package and
  `gallery-publish.yml` (released on `v*` tags) there, and a separate opf PR removes `packages/gallery`. Its npm trusted
  publisher is OpenPresentation / gallery / `gallery-publish.yml`, and 1.0.0 publishes from there. 2.0.0 is this redesign.
- **The records are authored there**: 28 short declarative layout files in the v2 syntax, written by hand and reviewed as
  code, released as `@openpresentation/gallery` **2.0.0** (a major: ids removed and the record schema changed,
  `CATALOG_SCHEMA` 2). Core and the CLI depend on `@openpresentation/gallery@^2`.
- **pptx.gallery consumes the npm package** for its browse and preview pages. It keeps only its display-only `x-gallery`
  fields (for layouts today: `label`, `master`, `masterSlideIndex`, `groupHash`, `groupDefault`, `zones`, `details`,
  `category`, `spatialCategory` and `contentTypeTags`) and retires its record-generation pipeline.
- **This resolves the RR-78 authoring blocker.** Today pptx.gallery generates the catalog records from its own page data:
  `data/<dimension>.json` holds the OPF fields beside the gallery-only fields, and `scripts/build-opf-catalog.mjs` with
  `lib/opf-catalog.mjs` projects them into `public/<kind>/` with `x-gallery`, which about 65 app files read. Authoring
  records in the gallery repository would have meant inverting that pipeline and taking authoring away from pptx.gallery.
  With 28 short declarative templates written in OpenPresentation/gallery, pptx.gallery instead consumes the npm package,
  keeps only its display-only `x-gallery` fields, and retires its record-generation pipeline.
- The stability check gets a fixture builder for templates: a slide with sample content for every region (three blocks in a
  flowing region, one in a `none` region), and a second slide with every region empty, which exercises collapse.

2. **Should the editor show roles, or just "drop content here"?** Recommendation: "drop content here" on slides, with the
   accepted kinds as icons; roles appear only in the grid editor, where a template's author sets them.
3. **Block sizing inside a flowing region.** Recommendation: region level only in 0.19 (track sizes, `flow`, `max`). A
   slide's `composition.weights` still sizes its primary region's tracks. Per-block spans can come later without a break.
4. **`itemImage`.** The `-itemimage` records set `listBullet: "image"`, which exists. Recommendation: no `itemImage` key; if
   the owner meant a picture per item (icons on pillars), that is a content field on list items, for a later minor.
5. **A `mirror` setting.** Every "beside" layout puts the picture, chart or table at the start; the other side needs a custom
   layout. Recommendation: add `design.mirror: true` in 0.19 (each row's cells and the column sizes reversed; logical, so a
   right-to-left deck still mirrors on top), the one design key this design adds beyond the six.
6. **Promoted regions** (`left`, `top:left`, ...). Recommendation: keep them in 0.19 as they are; decide in 0.20 whether
   custom layouts replace them.
7. **Which layouts the PPTX carries.** Recommendation: every built-in plus the deck's custom ones (28 small parts), so
   Change Layout can reach any of them; an export option for "used only" if file size becomes a complaint.
8. **The other catalog kinds.** Recommendation: themes, colour schemes, font schemes, narratives, audiences, purposes and
   tones are authored in OpenPresentation/gallery from 2.0.0 too, seeded once from pptx.gallery's current records, so its
   whole record-generation pipeline retires at once rather than for layouts only.
9. **Multi-line titles in the native title placeholder.** Recommendation: measure in the phase 3 native check whether
   PowerPoint wraps the bundled fonts at core's accepted points; if it does on the gallery fixtures, make every plain title
   native in a 0.19 patch; until then follow RR-11's one-line rule.
10. **Foreign PowerPoint layouts as custom templates.** Recommendation: not in 0.19. Snapping a foreign layout's
    placeholders to a grid is possible but needs its own evidence; 0.19 maps by type and name.
11. **The schema id.** Recommendation: `opf-layout/v2` and `CATALOG_SCHEMA` 2, so a v1 record is rejected by its id, not by
    a confusing missing-field error.
12. **`title` and `title-subtitle` slides become centred** (they set no alignment and `cover` centres). Recommendation:
    accept; the Markdown example and most decks use them as covers.
13. **Diagram intents.** 13 records named for diagrams map by what they hold (`gallery`, `text`, `chart`, `process`,
    `hero`). Recommendation: accept for 0.19; a diagram content kind ([diagrams plan](../../plans/diagrams-svg.md)) would
    bring a `diagram` layout with it.
14. **The `auto` threshold** (6 lines). Recommendation: keep the rule, tune the number on the gallery fixtures and the 103
    examples before the release, and record the tuned value here.
15. **Business model canvas.** Recommendation: ship it as the worked custom-template example in the docs and examples, not
    as a built-in.
