## What the spikes and the repository reading found

Read on 2026-10-20 and 2026-10-21 from `origin/main` of each repository and the GitHub API (read-only). The spike reports are in `artifacts/monorepo/` (`spike-S1-S6.md`, `spike-S2-S3.md`, `spike-S4-S5.md`; scripts `spike-S2-filter-repo.sh`, `spike-S2-verify.mjs`); the owner's local sibling checkouts are stale and no number comes from them. 1. **Goldens are hash manifests, not images.** opf-render's `test/golden/**/*.sha256.json` (2,843 small files) are SHA-256 manifests; PNGs are regenerated in the pinned Playwright image. History weight is `docs/evidence`, fonts and fixtures. The largest blob in any history is 6.8 MiB (a core evidence PNG; siblings: 2.3 MiB). **LFS is not needed.**
2. **The import is cheap and exact (S2).** `git filter-repo` rewrites each sibling in under 1 second (about 30 seconds of compute in all, including clones and verification). Tree hashes are equal at all 818 sibling commits and 149 sibling tags; author, dates and parents are preserved; blame is identical on 150 sampled files; the rewrite is deterministic, and a delta re-sync after the old repo gains commits merges only the new commits (under 15 seconds). The merged repository has 1,738 commits and 226 tags, a 166 to 168 MiB packed history and a 508 MiB tracked tree (370 MiB of it `docs/evidence`). A blobless, sparse clone without `docs/evidence` takes about 2 seconds and 190 MB on disk; `fetch-depth: 1` saves under 10 percent. Gallery is tiny (10 commits, 5 tags, 425 files, +436 KiB packed; npm and `package-lock.json`, two workflows `ci.yml` and `gallery-publish.yml`, 2 open issues, 1 open PR) and imports the same way (S7: filter-repo 0.2 s; tree hashes equal at `main`, all 5 tags and all 10 commits; blame identical on all 425 files; deterministic).
3. **Messages need a rewrite (S2).** Bare `#N` references become `OpenPresentation/<old-repo>#N` (262, 282 and 195 in render, pptx and editor); the 4 closing keywords get the word `issue` inserted so no imported commit can close anything; filter-repo also rewrites 7 embedded commit hashes (keep); 4 messages that say "core #N" are mis-attributed unless `OPF_IMPORT_CONTEXT_REFS=1` is set (use it).
4. **pnpm for the siblings is a GO with no overrides (S1, S6).** `pnpm import` reproduces each `package-lock.json` exactly (487 of 487 shared name and version pairs, identical integrity). A combined workspace resolves every direct dependency of the siblings to today's version; only 7 to 22 unpinned transitive packages per sibling shift (3 patch bumps, 1 patch downgrade, one deduped optional canvas bump), accepted as **one reviewed lockfile commit**. All 400 sibling unit tests run under pnpm's default isolated layout with zero phantom-dependency failures; the only failures are workflow-contract tests that read the `.github/` the plan deletes and one golden-corpus mismatch (digest `70b9e5d4` against the recorded `22ebe285`: the MR-31 reconciliation). `node-linker=hoisted` is worse (13 more failures) and the v1 fallback is dropped. Exactly 45 `@expo-google-fonts/*` packages are pinned across the manifests with zero conflicts.
5. **Mechanical fixes that pnpm needs (S1, S4, S6)**, all small: (a) pptx `scripts/verify-vendor.mjs` reads `package-lock.json` and fails `pnpm pack`; it must read the `@node-projects/jszip` integrity from `pnpm-lock.yaml` (3 lines; the value is identical); (b) 7 files assume npm through `npm_execpath` (render `test/packed-install.mjs`, `scripts/check-next-bundle.mjs`, `scripts/update-font-manifest.mjs`; pptx `test/packed-install.mjs`, `test/provenance-interop.mjs`, `test/packed-bundle-browser.mjs`; editor `test/packed-install.mjs`); (c) the three `test:packed` suites read raw `workspace:` specs and must read the packed manifest; (d) 28 `package-lock.json` references, mostly pptx `native-*` evidence hashes; (e) pptx `test/color-ref-export.mjs` silently falls back to an inline fixture when `../../opf/docs/fixtures/color-references.opf.json` is missing (silent coverage loss), and render `scripts/probe-font-variants.mjs` imports `../../opf-pptx/...`; grep `../../opf`, `../opf`, `../../opf-` in sibling `test/` and `scripts/` and fix each to the workspace layout.
6. **Sibling tests that read the deleted `.github/` contracts** are deleted or rewritten: `candidate-gallery-ci` (all three), `publish-source` and `publish-workflow-trust` (all three), render's `candidate-goldens` and `golden-pinned-image`.
7. **Do not use `catalog:` for fonts (S1).** Seven scripts and tests read `devDependencies[...]` as literal versions (render `test/font-licenses.mjs`, `test/script-fonts.mjs`, `scripts/update-font-manifest.mjs`, `scripts/check-next-bundle.mjs`, `test/packed-install.mjs`, the pptx and editor packed-install tests). Fonts and the devDependencies that mirror an optional peer (`sharp`, `@resvg/resvg-js`, `pdf-lib`) stay **exact literal pins**, guarded by a root check `check:pins` (all manifests agree on every shared exact pin; each package's peer pin equals its own devDependency pin). `catalog:` is only for `playwright`, `esbuild`, `axe-core`, `pdfjs-dist`, `@napi-rs/canvas`, `@hyzyla/pdfium`, `@jspawn/qpdf-wasm`, `jszip`, and is optional (Dependabot catalog support is documented as GA but unverified in this repository).
8. **Packing (S4).** `pnpm pack` produces publishable tarballs for all packages; `workspace:^` becomes `^<version>`, `workspace:*` becomes the exact version, `catalog:` becomes the literal version, peers written as `workspace:^` also rewrite. **`gitHead` is absent from `pnpm pack` tarballs** (npm adds it only for directory publishes), so the build must stamp it. The packed core and CLI `repository.url` is `https://...opf.git` while npm needs the exact `git+https://github.com/OpenPresentation/opf.git`. Committed `dist/` in the siblings is reproduced byte for byte by the pack-time rebuild (a drift check must run after the build, because `pnpm install` flips one file's mode).
9. **Trusted publishing (S4).** npm allows **up to 10 trusted publishers per package** (v1 assumed one), so the new entry is added beside the old one and rollback needs no owner action. The OIDC token is exchanged per package, so each of the six packages needs its own entry for `OpenPresentation/opf` and `npm-publish.yml`. Dist-tag operations through OIDC need npm 11.21.0 or later, so tags are set with `npm publish --tag`. The 11.16.0 pin is only needed in the release job (pnpm has no optional-peer re-resolution problem; the siblings' `npm install -g npm@11.16.0` lines disappear with their `.github/`).
10. **The package graph (S4, S5).** A cycle exists today: core declares optional peers and exact devDependency pins on render and pptx. With `workspace:` links pnpm only warns, but renderer and PPTX changes then select all packages and the topological order degrades; `link-workspace-packages=true` re-creates the cycle silently. With acyclic manifests `pnpm --filter "...[origin/main]"` selects exactly the right packages (editor-only: editor; CLI-only: cli; render: render, pptx, cli, editor; pptx: pptx, cli, editor; core: all). Everything outside `packages/*` (`spec/`, `examples/`, `skills/`, embedded docs, `scripts/`, workflows, the lockfile) maps to the root project, which selects nothing, so `ci-scope.mjs` must own a path map.
11. **v2 adds a second cycle to avoid: gallery.** Core and the CLI depend on gallery at runtime, while gallery's own manifest has devDependencies on core and render (it validates its records against core's schemas and draws its previews with the renderer; its `scripts/bootstrap-*.mjs` and `.github/bootstrap-engines.json` exist only because those engines were unpublished). In one workspace that is core to gallery to core. The rule in section 1, rehearsed in S7: **the gallery package has no workspace dependencies**. Its engine-dependent gates (`check:previews`, `check:stability`, the 9 tests that need `opf-render`) run from the repository root, where `@openpresentation/opf` and `@openpresentation/opf-render` are root `devDependencies` (`workspace:*`); the gallery's scripts resolve the engines with `createRequire(<packageRoot>/package.json)` and Node's lookup walks up to the root `node_modules`, so no script change is needed. The graph stays acyclic (gallery, core, cli): `pnpm install` 1.4 s, no cycle warning, `pnpm ls -r` shows `@openpresentation/gallery@link:../gallery` in core and the CLI. `ci-scope.mjs` needs one explicit non-manifest edge ("a change in core or render re-runs the gallery gate"), because the pnpm filter graph cannot see it. `build.mjs` imports no engine (it inlines records and previews), so nothing has to be split out of the build.
12. **`packages/gallery/` already exists as a generated, gitignored directory** (`scripts/materialize-gallery-catalog.mjs`, the root `postinstall`, writes the `catalog/` and `previews/layouts/` snapshot there from the installed npm package, guarded by a marker file `.generated-from-openpresentation-gallery`; about 20 files read it: `catalog-snapshot.mjs`, `check-catalog-free.mjs`, `check-spec-integrity.mjs`, `check-breaking-changes.mjs`, `check-schema-examples.mjs`, `snapshot-tracker-catalog.mjs`, `build-gallery-tracker.mjs`, `ecosystem-records.mjs`, `published-matrix/*`, `gallery-catalog/*`, a core test, the issue and PR templates, three schema descriptions). ## Goal

> One repository, one version, one fast PR check and one-click release for core, CLI, renderer, PPTX exporter, editor and gallery, with the same npm package names and public APIs, so that consumers see no change except one coherent version number.

Targets (measured, not assumed; section 4 and 5):

- **PR check: about 5 to 8 minutes p50** ("verify", the only required check), p90 at most 12.
- **Train: about 20 minutes** from the click (or the tag) to all six packages published and verified, with no agent attention.
- **Slow checks** (Windows, macOS, Node 22 and 26, packed-install and published-matrix consumers) cost PRs nothing: nightly, plus once before every release.

What it removes: the ecosystem lock and roller, `Depends-On`, the candidate-gallery lanes and the gallery-major dance, the published-control bridges, `release-plan.json`, `opf.requiresUnreleasedCore` and the RR-55 gates, golden overrides, the merge queue and its fast path, per-package patch drift and peer-range chores, and most of `release-train.mjs` and `pr-gate.mjs` (section 2).

Staying separate, by decision: only the three sites (Data-Advantage/openpresentation-site, pptx-gallery, pptx-dev). Records are authored by pull requests in `packages/gallery` (S7: the documented pptx.gallery to gallery sync never ran, so there is nothing to repoint); pptx.gallery consumes the published `@openpresentation/gallery` package.

## Definition of done

1. `OpenPresentation/opf` is one pnpm workspace with `packages/javascript` (core, D2), `cli`, `render`, `pptx`, `editor` and `gallery`, plus a private, unpublished `packages/integration`, with the full imported history of the four old repos (tree hashes at every tag and commit identical to the originals, blame intact, tags preserved).
2. A change that touches several packages is **one pull request**, tested by one `verify` run, merged on green. None of these exists any more: `Depends-On`, a lock-roll PR, a golden override, `requiresUnreleasedCore`, a candidate-gallery lane, `release-plan.json`, a merge queue.
3. `verify` is the one required check and meets its target on at least 20 measured runs.
4. `nightly.yml` runs every slow check; a failure opens (or updates) one issue and never blocks a PR; the release workflow runs the same set once on the release commit before publishing.
5. A single `npm-publish.yml`, started by a `workflow_dispatch` or a pushed `v*` tag, versions all six packages, assembles the changelogs from `changes/`, builds and packs once, smoke-tests, publishes all six with npm trusted publishing and provenance, verifies them and creates the GitHub release. Two consecutive releases were done this way, within the target.
6. After a release a bot opens "bump to vX.Y.Z" PRs on the three sites; patch bumps auto-merge on green.
7. Public contracts unchanged: package names, `exports`, install docs, `npm view` metadata other than `repository`, `bugs`, `homepage` and the version number (D16: one shared version from 0.26.0; the gallery's number goes backwards from 5.0.0).
8. The four old repos are archived read-only with a README pointer, open issues transferred, open PRs ported or closed; the sites and docs point at the new locations; `docs/release-process.md`, `docs/ecosystem-development.md`, `AGENTS.md` and `CONTRIBUTING.md` describe the monorepo only.

## Invariants

- **Nothing moves before CLI 0.25.0 is verified.** The plan itself is decided (D1 to D20). After that, work proceeds only by the phases below; OWNER actions are the owner's.
- **`main` of `OpenPresentation/opf` is green and releasable after every phase, and every phase is reversible** (section 9 gives each rollback). Until the cutover in Phase 4 the existing release process keeps working for core and the CLI; sibling releases are on hold from the import (MR-22) to the first shared release (MR-44), expected at most two working days.
- **Consumers see no change** other than the shared version: package names, entry points and `exports` are untouched. Migration PRs change no package behavior. Allowed manifest edits: `repository`/`bugs`/`homepage`, workspace-protocol dependencies and peers, the removal of `opf.requiresUnreleasedCore`, the removal of gallery's engine devDependencies, and the pnpm conversion of scripts.
- **Every publish goes through npm trusted publishing (GitHub Actions OIDC) with `--provenance`** from the top-level `npm-publish.yml` (npm matches the calling workflow's filename; the publish step never moves into a reusable workflow). No `NPM_TOKEN`, no local publish, no publish from an unmerged branch.
- **The old repos stay public, un-renamed and un-deleted forever**, and keep their trusted-publisher entries until the soak ends. Tags are never moved or re-pushed.
- **History is merged, never squashed.** The import uses `git filter-repo` on scratch clones, never the owner's checkouts under `/Users/michael/Source/`.
- **Goldens stay exact.** No tolerance changes; golden files move byte for byte (hash-checked); no baseline is regenerated in a migration PR; regeneration stays a workflow in the pinned Playwright image.
- **Coverage moves, it never disappears.** Every platform and Node leg that exists today runs nightly and before every release. Scoping fails closed: a path or case the scope script cannot classify runs everything.
- **The whole set is one version.** Packages are never released one at a time; the published set is "everything at tag `vX.Y.Z`".
- **No polling.** No workflow loops on another workflow, no agent polls CI: the release is one workflow run, PRs merge through GitHub auto-merge, and `pr-gate.mjs` (shrunk) is the only watcher.
- **No paid runners.** Standard GitHub-hosted runners only (free for public repositories; 20 concurrent jobs, 5 macOS).
- Agents never deploy, log in to a site host or change DNS (cloudflare-hosting invariant); they work in worktrees from fresh `origin/main` and never force-push `main`; measured numbers in this file are dated and re-measured before use.

### Gallery versioning and the stability rule (D16)

**Why the gallery used majors.** Under semver at 1.0.0 and above, a changed or removed record redraws existing decks, which is a breaking change, so the independent gallery needed a major for it (new records were a minor, anything that draws the same a patch). That is why it reached 5.0.0 in 11 days. On the shared 0.x line a breaking change is a minor bump (D14), so the same change is a minor bump there, which is why the replacement rule below says "minor train, never a patch".

**Publishing below 5.0.0 (S7, from the npm source).**

- `npm publish` refuses to move `latest` backwards implicitly ("Cannot implicitly apply the "latest" tag because previously published version 5.0.0 is higher than the new version 0.26.0. You must specify a tag using --tag."). It is not blocked: with an explicit `--tag latest`, `latest` moves to 0.26.0. The check compares against the highest version ever published, so **every** gallery publish (0.26.1, 0.27.0, ...) needs the explicit tag for as long as 5.0.0 exists, and so does the `0.26.0-rc.0` canary (to `next`). `npm-publish.yml` therefore passes `--tag <dist-tag>` for all six packages (`latest` by default); the tag must be set at publish time because OIDC dist-tag changes after the fact need npm 11.21.0 or later (S4 F5).
- **Publish gate in `scripts/release.mjs`** (`prepare` and the publish job): the version being published must be greater than the `latest` dist-tag's version of the same package for core, cli, render, pptx and editor. For the gallery it is compared against the shared line (the previous release's version, which is what the other five packages' `latest` carry) and not against the highest semver, which would be 5.0.0 and refuse every release; `check:versions` already asserts that all six manifests carry the same version.
- **5.0.0 and 1.0.0 to 4.0.0 are not deprecated and keep their dist-tags.** Published core 0.25.0 depends on `^5.0.0`; a deprecation would print a warning on every install of it. `^5` consumers keep resolving 5.0.0 and get no further catalog fixes (every known consumer is ours; the sites' `^4` and `^5` ranges are edited by the bump bot). `npm install @openpresentation/gallery` installs `latest`, 0.26.0, and writes `^0.26.0`. `npm outdated` shows "latest 0.26.0" below "current 5.0.0", `ncu` and `pnpm update --latest` propose it as a downgrade, and Dependabot and Renovate ignore it. Optionally the owner adds a dist-tag `v5` pointing at 5.0.0 so `npm view @openpresentation/gallery dist-tags` explains the old line.
- **The shared line can never use 1.0.0 to 5.0.0** (gallery versions 1.0.0 to 5.0.0 are taken), so when OPF wants a 1.0 the shared version for all six must jump to **6.0.0** (or the gallery package must be renamed). This is recorded in the version policy and accepted with D16.

**The stability rule, replaced (new item MR-35, gating the first shared train).** Today `scripts/stability.mjs` derives "previous release" from the highest published stable version at or below the candidate and allows a drawing change only across a major. Run against a shared 0.x version it picks `0.0.1` as the previous release and forbids every change, so it cannot survive as written. The replacement keeps the purpose (a drawing change or a removal is deliberate, visible and never hides in a patch) with the version the train already chooses:

1. **A declared drawing change.** `check:stability` keeps drawing the previous release and the candidate with the same workspace engine and computing `added`, `removed` and `changed` ids per kind, and the `CATALOG_SCHEMA` comparison. The verdict changes: every id in `removed` or `changed` must be named in a changelog fragment for the gallery (`changes/<slug>.md` with `packages: [gallery]` and a front-matter list such as `drawing: ["layouts:hero", "themes:minimal"]`). An **undeclared drawing change fails the PR**; a declared id that did not change warns; `check:changes` validates the field; the CHANGELOG bullet lists the ids.
2. **A declared drawing change forces a minor train, never a patch.** `release.mjs prepare` and the release `gate` read the fragments being assembled: a `drawing` entry, a removed record id or a `CATALOG_SCHEMA` change requires the train version to raise the minor (0.26.0 to 0.27.0), never a patch (0.26.1). New ids and unchanged drawings are allowed in any train.
3. **The baseline is the `latest` dist-tag, not the highest semver**: `npm view @openpresentation/gallery@latest version` (or the last train's tag). For the first shared train the baseline is 5.0.0; the engines read the 5.0.0 records and `CATALOG_SCHEMA` is 4 on both sides, so the comparison is direct.
4. **Core's `check:breaking` enforces removed record ids.** It flags a removed `packages/gallery/catalog/<kind>/<id>.json` against the last release tag and accepts it only with a version bump. Today the directory is untracked, so it sees nothing; tracked, it enforces "a removed id is breaking" for free. MR-35 checks that its tag listing works for tags created after the import.
5. **`CATALOG_SCHEMA` and `opf.catalogSchema` stay** (public contract for third-party catalogs and the sites). The runtime refusal `gallery-schema-mismatch` (`galleryMismatch` in `packages/javascript/src/node/catalogs.ts` and `packages/cli/src/catalogs.ts`) existed because core and the gallery were versioned independently; under one version `workspace:^` makes the shipped pair `^0.26.0`, and the existing equality test (`packages/javascript/test/gallery-default.test.mjs`) plus a root check cover it. Removing the refusal is a behavior change, so it is its own item after the first shared train (MR-62), not part of the move.
6. **Until MR-35 lands, `check:stability` cannot be a required check** (it fails every change on a 0.x version), so the gallery job runs everything else (license, verify, build, test, typecheck, `check:previews`, pack) and the first shared train waits for MR-35. S7 did not run `check:previews`, `check:stability`, `typecheck` or the 9 engine-dependent tests (no renderer in its scratch), and the rule is a design, not code; MR-35 writes and tests it (the existing 168-line `stability.test.mjs` tests the old rule).

## 4. CI: one fast check, slow checks off the critical path

**`ci.yml`** (`pull_request`, `push` to `main`, `workflow_dispatch`; no `merge_group`) with one required check, **`verify`**, an aggregator job that succeeds only if every job the scope selected succeeded (skipped by scope is success, skipped otherwise is failure). **`nightly.yml`** (schedule, dispatch, `workflow_call`) holds the slow set and is also what `npm-publish.yml` calls once on the release commit and what `ci.yml` calls for the label `full-ci`; **`slow-checks.yml`** (weekly, dispatch, label `slow-checks`) holds what tests the published packages or needs a long run (published matrix, installed parity, the full golden corpus). MR-30 realized it in that split; file-by-file design notes, the job graph and the timing budget are in [ci-design.md](ci-design.md).

**`verify` contents** (target 5 to 8 minutes p50):

1. `scope` (about 30 seconds, no install): `scripts/ci-scope.mjs` builds the package graph from the six manifests (the same edges as pnpm's `--filter "...[origin/main]"`; a unit test cross-checks it on the six S5 scenarios), maps changed paths to packages (`packages/<x>/**` to `<x>`; `spec/**`, `examples/**`, `skills/**` and the `docs/**` files core embeds to core; `packages/gallery/**` to gallery (the tier decision treats `packages/gallery/{catalog,previews}` like core's `spec/`, since render, pptx and the editor import the gallery in about 44, 52 and 61 source and test files and a layout or theme drawing change moves goldens; confirm the tier in MR-14); `scripts/**`, `.github/**`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `package.json`, `biome.json`, `.nvmrc`, `.gitattributes` to **all**; `docs/programs/**` and `docs/evidence/**` (except `*.opf.json`) to **none**; anything unclassified to **all**), and emits `changed` and `affected` (changed plus transitive dependents). Changed packages run `full`; dependents run their `test:contract` suite (RR-53's `contractExclude`); a `scripts/**`, lockfile or `full-ci` change runs `full` everywhere. Every package depends on core and core on gallery, so a gallery or core change affects all six, at contract tier for the dependents.
2. `lint`: Biome and the root `check:*` suite (spec, schema, text, workspace-graph, pins, versions, playwright-pin, changes warning, engines-range, catalog and tracker checks), plus `typecheck`.
3. Total shards are sized so that the longest job, not the sum, sets the time.

No "require branches to be up to date" rule: with merge on green, two PRs that are green alone can fail together, and the push run on `main` is what catches it within minutes.

## 5. Release: one click

**One workflow, `.github/workflows/npm-publish.yml`.** Two entries, one pipeline:

- `workflow_dispatch` with inputs `version` (`X.Y.Z`, or `patch` / `minor`) and `dist-tag` (default `latest`; `next` for a canary prerelease such as `0.26.0-rc.0`): **prepare, then release**.
- `push` of a tag `v*`: **release only**, from a commit that already carries the release commit (the fallback when someone prefers a PR, and the retry path after a failure: re-run the workflow on the tag).

```yaml
on:
  workflow_dispatch: { inputs: { version: {...}, dist-tag: {...} } }
  push: { tags: ['v*'] }
permissions: { contents: read }
concurrency: { group: publish, cancel-in-progress: false }
jobs:
  prepare:   # dispatch only. App token (bypass on main). Checks that main's `verify` is already green for HEAD (one API call, no waiting;
             # otherwise fail at once). scripts/release.mjs prepare: bump the six manifests (check:versions), assemble every changelog
             # from changes/ fragments (changelog-fragments.mjs; untouched packages get "no package changes; released with the set"),
             # delete the consumed fragments, the gallery stability gate (MR-35: a declared drawing change, a removed record id or a `CATALOG_SCHEMA` change needs a minor bump, never a patch), the publish gate (version above each package's `latest`, the gallery against the shared line), commit
             # "release vX.Y.Z" and push it to main, output the commit.
  gate:      # on the release commit: ci-scope forced to "all, full" (verify) and nightly.yml (Windows, macOS, Node 22/26, packed-install on the
             # tarballs of `build`), in parallel with `build`. A red leg stops the release before anything is published.
  build:     # one install, one build, `pnpm pack` of the six, scripts/stamp-githead.mjs (adds gitHead = the release commit to each tarball's
             # package.json: pnpm pack and `npm publish <tarball>` omit it, S4), tarball smoke (install all six in a clean consumer, run the
             # quickstart), upload-artifact tarballs.
  publish:   # needs [gate, build]; permissions: id-token: write only here; Node 24 and npm 11.16.0; explicit order gallery, core, render,
             # pptx, editor, cli (not pnpm's order, S4 F7), max-parallel 1, fail-fast; `npm publish <tarball> --access public --provenance
             # --tag <dist-tag>` (the tag is explicit for all six, `latest` by default; mandatory for the gallery, D16); skips a version already on npm (a re-run continues where it stopped). No secrets, no App token.
  verify:    # scripts/release.mjs verify for all six: registry manifest, gitHead and provenance source commit equal the release commit,
             # provenance workflow npm-publish.yml on refs/tags/vX.Y.Z, signatures, dist-tags, then a published-matrix smoke on the registry set.
  release:   # contents: write only here; creates the tag vX.Y.Z (dispatch path) and the GitHub release with notes grouped by package; on any
             # failure, opens an issue "Release vX.Y.Z failed" with the run URL.
```

- **Implementation note (MR-40).** The sketch above has `npm-publish.yml` do the `prepare` step and the release in one run. npm validates a trusted publisher against the top-level (calling) workflow, so a `release.yml` that called `npm-publish.yml` as a reusable workflow would have to be the publisher, with provenance not naming a tag. As built: `release.yml` (dispatch: `version`, `dry-run`) runs `plan`, `gate` (`nightly.yml` as a workflow call, parallel with `prepare`), `prepare` (a patch artifact, fails fast) and `commit` (the App token pushes the release commit to `main` and then the tag `vX.Y.Z`, which starts `npm-publish.yml`, the trusted publisher: `plan`, `build`, `publish`, `verify`, `release`, `report`); a dry run dispatches `npm-publish.yml` with `dry-run=true`. Retry and fallback are unchanged (D6). See `docs/release-process.md`.
- **Why the bypass.** `prepare` commits to `main`, which the ruleset protects. The release job mints a GitHub App installation token (the existing ecosystem App, repurposed; OWNER action) that is a bypass actor on the `main` ruleset, so the release commit lands without a PR and without a second run of CI. Only the `prepare` job holds the token; the `publish` job holds no secret. If the owner prefers no bypass, the PR path remains: run `pnpm release:prepare X.Y.Z` locally (an agent task), merge that PR on green, and push the `v*` tag.
- **One version, one tag, one changelog model.** `changes/<slug>.md` keeps its front matter (`type: added|changed|fixed`, `packages: [opf, cli, render, pptx, editor, gallery]`). `changes/config.json` `targets` extends to all six (`opf` root `CHANGELOG.md`, the others `packages/<x>/CHANGELOG.md`, gallery's imported with its history) and `codePaths` to each package's source; `check:changes` rejects unknown names; CI warns per package. The assembler writes the release section into every package named by a fragment; a package with no fragment gets one line (so every package changelog has every version, and `verify` can check it). The GitHub release body is the union grouped by package. In 0.x a breaking change is a minor release.
- **Retry is idempotent.** A failed run is fixed and re-run on the same tag; versions already on npm are skipped. A real defect is fixed forward with the next patch and a new tag; tags are never moved. A partial publish is safe under semver because the `^X.Y.Z` floors point at versions that exist (publish order is dependency order).
- **Verification replaces `ci-evidence`.** Because the gate runs the checks on the exact release commit, nothing trusts an earlier run, so `ci-evidence.mjs`, its JSON and the queue-run requirements disappear.
- **Time (target about 20 minutes, p90 30; measured in MR-44).** `prepare` 2 + `build` about 5, with `gate` in parallel (verify at full tier about 10, slow set about 12 once its legs are sharded to at most 12 minutes each; a leg that cannot fit is measured in MR-32 and stays nightly-only, stated in the release notes) + `publish` about 3 (six publishes, about 30 seconds each) + `verify` about 4 (provenance and registry propagation, bounded inside the job) + `release` 1. Today: about 65 minutes of serial publish compute, four prep PRs each through CI and a merge, 5 to 6 hours elapsed, about 15 minutes of agent attention.
- **Failure classes removed.** The 3 failed publishes this week came from release ordering and per-repo lockfiles waiting for an upstream version on npm. With one repository, one lockfile and one version, no step waits for another package to appear on npm.

## 6. Sites auto-update

Goal: after a release the three sites (Data-Advantage/openpresentation-site, pptx-gallery, pptx-dev) get a "bump to vX.Y.Z" PR without anyone watching; their own checks are build plus smoke; patch bumps merge on green, merged by the site's own CI (D19). Sites pin exact versions of the packages they use (for example `@openpresentation/opf-render` in all three, `opf-editor` in two, `cli` in one) and a range for gallery, so every bump is a manifest edit plus a lockfile refresh.

**Decided (D17): `bump-sites.yml` in the opf repo.** **As built (MR-52):** `bump-sites.yml` is a `workflow_call` from `release.yml` (its `sites` job, after the `watch` job saw the whole `npm-publish.yml` run succeed, for a stable version only) and a `workflow_dispatch` (version, dry-run, sites) for a re-run or a release made by the fallback path. It is not started by a `workflow_run`: `release.yml` already follows the publish run, a `workflow_run` would fire on a dry run and on a canary too, and the tag-fallback path has no caller (use the dispatch). A separate workflow still keeps the App secret out of the publish workflow (`npm-publish.yml` holds no secret). **Site scripts (as built, 2026-10-24).** A script-only pin bump left two sites red on their own CI (the first real bump, 0.26.1: openpresentation-site #146, pptx-gallery #151, pptx-dev #152), because each site derives files from the packages that only the site knows about. So each site owns ONE script, `pnpm opf:bump <X.Y.Z> [--opf <checkout of this repository with the tag>]` (`scripts/opf-bump.mjs` in the site), that does everything the site needs, deterministically, and `bump-site.mjs` only decides the label from the pre-bump pins and calls it. `openpresentation-site`: the pins of the root and the four `starters/*`, `opfSource` (version and the commit of the tag `vX.Y.Z`; the site's fallback ref for an unpinned install is now the tag `vX.Y.Z`, not the retired `opf-vX.Y.Z`), the lockfile, `data/releases.json` (the five packages with the registry publication time and a summary from the GitHub release notes of the tag, a `coreHistory` entry for every stable core version still missing, `verifiedOn`; a prerelease on the registry is ignored), the `.opf-source` snapshot and `public/homepage-details/manifest.json`, then `verify-releases`. `pptx-gallery`: the pins, the lockfile, `import-font-replacements` and `sync-preview-fonts --core-repo <checkout> --core-ref <commit of the tag>` (never a sibling checkout's `origin/main`), the package catalog and layout previews, `build-chart-previews`, and the editor bundle and schema reference through this repository's `scripts/vendor-gallery-editor.mjs` at the tag, then the checks of its CI that read them (`--check` of each generator, the lazy fonts, the published-editor verifier). `pptx-dev`: the pins, `opf-reference-layer-pins.json` (packages, `opfSourceRef` = the commit of the tag, description) and the lockfile. Each script is idempotent and was checked by running it on the pre-bump state of the 0.26.1 bump and on the merged 0.26.1 state for the real 0.26.2 bump (the site pull requests carry both) (the merged pptx-gallery result is reproduced byte for byte, the other two match their pull requests apart from the generated summaries). Two things stay outside any script and fail the site's CI instead of being papered over: a release that changes behavior a site's tests assert (0.26.1 changed editor keyboard handling), and advisories published after the lockfile was last resolved (`pnpm audit`). The site is checked out without credentials; the App token is used only for the push and the pull request. For each site repository `bump-sites.yml` mints a token with `actions/create-github-app-token` (the App's installation on that repo), runs `scripts/bump-site.mjs` (which runs the site's script with the site's own pnpm), pushes `bot/opf-vX.Y.Z` and opens the PR titled **"bump to vX.Y.Z"**. If the version change is a patch (same X.Y) nothing more is done here: the site's own CI merges the pull request once its `build-and-smoke` job has passed (D19, below); a minor or major bump (a breaking change in 0.x) is labelled `needs-review` and left open, and the site's CI never merges a pull request carrying that label. `bump-sites.yml` never calls `gh pr merge --auto`: the sites are private repositories in the Free-plan `Data-Advantage` organization, which has no rulesets, no branch protection and so no required check, and `--auto` without one merges at once. It is atomic (all six packages, after `verify`), idempotent (an existing branch is updated), and a failure to bump never fails the release (the job only opens an issue). App-authored PRs trigger the sites' CI, which `GITHUB_TOKEN` PRs would not.

## Resume protocol

Any session resuming this program:

1. Read this file and `burndown.md` (its progress log is the latest state). The plan is decided (D1 to D20). If CLI 0.25.0 is not yet verified (`npm view @openpresentation/cli dist-tags.latest` is not 0.25.0, or its release verification has not passed), **do nothing but read**.
2. `git fetch` every repository in scope and work only from fresh `origin/main` worktrees. Never switch, clean or run the import in the owner's checkouts (`/Users/michael/Source/*`; some are stale). The import runs only in a scratch directory. After MR-20, the old repos accept only the changes listed in section 7.
3. List open program PRs with one batched query (respect the shared 5,000-per-hour GitHub quota in `AGENTS.md`).
4. Pick the lowest-numbered `todo` item whose dependencies are `done` and that is not an OWNER item. Branch `codex/mr-<nn>-<slug>`; PR title `MR-<nn>: `. Watch PRs only with `node scripts/pr-gate.mjs`.
5. An item is `done` only when its acceptance criteria hold and its evidence is linked. Items that need an npm setting, a GitHub setting, a ruleset, an App permission, an archive, a secret or a deploy are the owner's: prepare the exact steps in `docs/programs/monorepo/owner-steps.md` and stop. Agents never publish by hand, never change trusted publishers, and never push to an old repo beyond the freeze list.
6. Never merge anything that changes package behavior as part of a migration item; split it out under its own item ID.
7. When an item changes state, update its row and append one dated line to the burndown progress log.
