LH-106 (output-changing for decks whose language has digits of its own, and for fractional numbers in decks whose language writes a decimal comma): numbers in languages with their own digits are now consistent. Every number the engines generate from a numeric value (a metric's value and delta, chart labels, ticks and percentages, table cells that hold numbers, list numerals and step badges, `{{slide.number}}` and `{{deck.slideCount}}`, number variables on a slide) is drawn in the numbering system of the slide's language, else the deck's, through one core function (`formatNumber`): an `ar-SA` deck now draws `٩٩٩` beside `١٬٠٠٠` instead of `999` beside `١٬٠٠٠`, `fa-IR` draws Persian digits, `bn` Bengali digits, and `ar-AE`, `ar-MA`, `hi-IN` and `en-*` Latin digits, with the locale's decimal and group separators and percent sign (`2,5` and `1.234,50` in German). Text the author typed is never rewritten. To choose Latin digits, tag the deck or slide with the standard BCP 47 extension `-u-nu-latn` (`"language": "ar-SA-u-nu-latn"`); `-u-nu-arab` chooses Arabic-Indic digits, and `opf/language-tag` warns about a numbering system OPF does not draw. The locale data is a table in core read from `Intl` once (`scripts/build-number-locales.mjs`), never at render time, so every runtime draws the same text. The export no longer fails on generated digits: an `ar-SA` deck whose text has no Arabic (a title "T" and the metric 1000) threw `OPFFontError missing-glyph`; `loadFonts({ scripts: 'auto' })`, `fonts.ensure` and `fonts.pending` now offer the faces of the digits each slide's language generates. PowerPoint's `lang` is written without the extension (`ar-SA`) and the tag as written comes back on import; a numbered list in Arabic-Indic digits exports as PowerPoint's `hindiNumPeriod` or `hindiNumParenR` auto-number (and imports as `arabic` numbering); a dataset table records the language its numbers were shown in, so its provenance still restores.
