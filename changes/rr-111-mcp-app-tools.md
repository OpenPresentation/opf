RR-111: the OPF viewer registers three MCP Apps app tools, so a host that calls tools in a view (Claude, with a remote connector) lets the model work on the deck that is already open: `read_deck` (revision, name, outline, selected slide and check findings, bounded for any deck, and the source in JSON, YAML or Markdown in pages under the 100,000-character result limit, each with a `textHash`), `select_slide` (by index or id) and `edit_deck` (1 to 100 JSON Patch operations with a required `expectedRevision`, applied as one undoable edit through the editor session). `edit_deck` changes nothing on a stale revision, while the user is typing (it never commits their open edit), over an invalid source draft, for an operation on the whole deck (`path` or `from` `""`) or on the whole slides array (any operation but `test` whose `path` or `from` is `/slides`), for more than 200,000 characters of operations, and for an edit that would make the deck invalid (the deck in the viewer is always valid: an invalid one does not open, and invalid source text stays a draft). In the source pane JSON keeps its formatting; YAML and Markdown are written again from the deck (YAML comments are dropped, and the pane says so). The definitions never change at run time, each tool acts on its own view only, mistakes in the arguments come back as results that say how to fix them, and the tools refuse with a clear result while loading, when no deck opened, after a newer viewer of the same deck replaced the view, and after teardown. Hosts without app tools keep the existing context updates and Send.
