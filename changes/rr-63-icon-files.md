RR-63 (breaking for hosts that register the gallery icon sets): a host pays for the icons its decks draw and for nothing else. In 0.33 `galleryIconSets` of `@openpresentation/gallery/icon-sets` was a catalog whose loaders imported a whole set as a module by a path every bundler follows, and core's Node defaults registered it, so any server bundle of core's Node build carried Lucide and Tabler (2.2 MB in an esbuild bundle; pptx.dev's Worker grew from 34.0 to 56.1 MiB between 0.32.1 and 0.33.0, about 6.4 MiB of it icon data) and a deck with three icons loaded two whole sets.
    - Now the icon data is plain static files in the gallery package under `dist/icons/`, exported as `@openpresentation/gallery/icons/*`: `<set>.json` (license, copyright, viewBox, style and every icon name: 33 KB for Lucide, 82 KB for Tabler), `<set>/<name>.json` (one icon, about 150 bytes), `<set>.icons.json` (the whole set: 364 KB, 99 KB gzip, for Lucide; 1,009 KB, 236 KB gzip, for Tabler) and `<set>.tags.json` (search keywords, read only by a search). The whole-set files add 335 KB to the package tarball (804 to 1,139 KB) and 1.37 MB unpacked (2.90 to 4.28 MB). `galleryIconSets` is a function: `galleryIconSets()` reads the installed files in Node, Bun and Deno; `galleryIconSets(load)` reads them through `load(path)`, and `fetchIcons(baseUrl, fetcher?)` is the `load` for files a host serves; `galleryIconSets({ lucide })` registers whole sets a server imported into its bundle. A deck reads each set's index once and one file per icon it names; a batch of more than 40 icons of a set (an icon browser's page) reads the whole set once, and so does a batch whose per-icon file is missing, so a host may serve only the six set-level files. `fetchIcons` takes a fetch function or a binding with a `fetch` method (`env.ASSETS`), refuses a relative base outside a page, and names the URL when a file answers 404, a web page (a single-page host's fallback) or text that is not JSON. `installedIconSets()` is `galleryIconSets()` where the installed files can be read and undefined elsewhere. The `@openpresentation/gallery/icon-sets/<id>` whole-set modules are removed.
    - Core's icon loaders are called with `{ icons: [names] }` (a search asks `{ tags: true }`) and may resolve with a record whose `names` lists every icon, whose `icons` holds the ones asked for and whose `errors` says why one could not be read; a loader that ignores the request and resolves with the whole record works as before. An icon that cannot be loaded never blocks drawing: `ensureIcons` does not reject, the icon is settled (not pending, so the renderer's fonts handle, the editor's font gate and the canvas draw the slide without it, and nothing asks for it again in a draw loop), and its `opf/icon-unknown` finding says which icon and why ("The icon lucide:truck could not be loaded: https://example.com/opf-icons/lucide.json answered 404."), also when the set loaded before; `ensureIcons(deck, { catalogs, retry: true })` asks again. What `ensureIcons` loaded is shared by every copy of core in a process, so a server that bundles core and keeps the engines external draws its icons. In Node the files are found next to the gallery module, else as the `@openpresentation/gallery` installed for the working directory, so a bundled Node server (ESM or CommonJS) deployed with its `node_modules` draws icons with no setup; without the files a set icon's finding names the folders it looked in and the remedies. A CommonJS bundle of core's Node build no longer fails to load the engines (it has no `import.meta.url`). `Catalog.iconSets` takes `IconSetLoader` functions.
    - Core's Node defaults, the CLI and the stdio MCP server register `galleryIconSets()`, so `convert`, `open`, `opf convert`, `opf validate` and the MCP draw and check icons with no setup, and a server bundle of any of them carries no icon data (an esbuild bundle of the Node build's `validate`: 6,429 to 4,239 KiB; the full MCP Worker: 32.4 to 30.2 MB). In a Worker, `@openpresentation/mcp`'s `defaultSources()` registers no icon set (there are no files to read), as the lean server does; a host that serves the files passes `sources.iconSets`.
    - The editor keeps the 0.33 contract: `await loadIconSets(editor)` loads the icons the deck draws, so `composeSlide` draws them. A set's icon is read on demand, so `setIcon` starts loading the icon it sets and returns `ready`, which a headless host awaits before the next `composeSlide` (the canvas waits by itself). `loadIconSets(source, ids, { icons, tags })` loads only the icons asked for, `listIconSets` gives a set's load `error`, `searchIcons` reports `unavailable` sets and rejects with `icon-sets-unavailable` when none could be read (the icon picker shows why instead of "no matches"), and the picker asks each set only for its own icons on the page. The playground registers the sets over the set-level files its build copies into `opf-icons/`.
    - What a host writes now: nothing in Node (core's defaults); `galleryIconSets()` where it wrote `galleryIconSets` in its own catalogs; `galleryIconSets(fetchIcons("/opf-icons/"))` in a browser page, `galleryIconSets(fetchIcons(new URL("/opf-icons/", request.url), env.ASSETS))` in a Worker, with `node_modules/@openpresentation/gallery/dist/icons/` (or only its `*.json` files) copied to `/opf-icons/` by its build. See docs/icons.md, "Loading", and docs/migrations/0.34.md.
