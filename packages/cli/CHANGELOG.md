## 0.25.0 (2026-10-21)

- FA-33: Core and the CLI use gallery 5 (theme variants; layouts as one list of regions). The `@openpresentation/gallery` dependency moves to `^5.0.0` (catalog generation 4), and the unreleased-gallery staging (`opf.requiresUnreleasedGallery` and `.github/candidate-gallery.json`) is gone.
- The optional peer ranges move to the 0.25 minor: `@openpresentation/opf-render` and `@openpresentation/opf-pptx` `^0.25.0`, matching core 0.25.0.
- FA-33 (breaking, no migration path): a layout record is one ordered list of regions. `areas`, `columns`, `rows` and the `regions` map are removed from `opf-layout/v2`; a record has a `direction` (`row` or `column`, default `column`) and a `regions` array of regions (`{ name, size?, ...rules }`) and splits (`{ direction, regions, size?, anchor? }`, up to three levels). `size` is a share of the parent (default 1; `auto` only in a column), `accepts` is optional (every body kind and `group`), `anchor` on the record or a split is inherited by body regions, and `title` and `subtitle` are reserved heading regions. Core compiles the tree into the grid composition has always used, so the 28 built-in layouts render identically (an equivalence test proves each compiles to its Gallery 4 grid and rules). A record with `areas`, `columns`, `rows` or a regions map is invalid. `opf/layout-template` and `opf/layout-region` cover the new rules, `layoutEntries` and the compile are in `@openpresentation/opf/composition`, and `CATALOG_SCHEMA` is 4 (Gallery 5). Examples, fixtures, docs and skills are converted.

## 0.24.0 (2026-10-20)

- The optional peer ranges move to the 0.24 minor: `@openpresentation/opf-render` and `@openpresentation/opf-pptx` `^0.24.0`, matching core 0.24.0.
- Breaking for documents that name the `dark` theme: the `@openpresentation/gallery` dependency moves to `^4.0.0` (RR-96), and Gallery 4 removes the `dark` theme because dark is now a `design.variant` of every theme. `design.theme: "dark"` is an unresolved reference (`opf/unresolved-reference`) and the deck falls back to the engine default theme. Use a theme with a dark variant instead, for example `{ "theme": "classic", "variant": "dark1" }`, plus `colorScheme: "boost"` and `fontScheme: "seaford"` for the old dark look. The gallery examples that named `dark` now use `classic` (with `variant: "dark1"` where the deck's own background is `dark1`), their embedded theme records carry the new `variants`, and seven layout previews are redrawn (`chart`, `chart-beside`, `code`, `dashboard`, `table`, `table-beside`, `timeline`). `CATALOG_SCHEMA` stays 3.
- Theme records (`opf-theme/v1`) accept an optional `variants` array of `{ id, name, variant }`, where `variant` is a value of `design.variant` (a background slot, or the `ColorVariant` object of `opf.schema.json`, referenced and not copied). Gallery 4 gives `minimal`, `classic` and `bold` the variants `light`, `light-alt`, `dark` and `dark-alt`. They are for pickers: a document keeps the chosen `variant` in `design.variant`, never the entry id, and the engines read only `design.variant`. The generated `Theme` type gains `variants?: ThemeVariant[]`, and the schema docs, the design-resolution and default-catalog docs and the opf-presets skill describe them.

- RR-75 (breaking, OPF 0.18): the CLI is consolidated around one convert command, one output convention and fixed flag meanings, with no aliases. Every removed command and flag is a usage error (exit 2, `code: "removed-command"` or `"removed-option"`) whose message names the replacement.
    - **`opf convert` absorbs the format commands.** `opf render`, `opf export`, `opf import`, `opf from-md`, `opf to-md`, `opf from-yaml`, `opf to-yaml` and `opf create --from` are removed: `opf convert <input> <output>` does all of them, the formats named by the extensions or by `--from` and `--to`. It reads stdin (`-`, with `--from json|yaml|md|pptx`, or JSON sniffed) and writes stdout (`-`, with `--to json|yaml|md|pdf|pptx|png|svg|zip`; png and svg take one slide). On its input side a plain `.md` file is OPF Markdown. Their flags moved with them, and a flag applies only where its format is involved, otherwise it is a usage error (`code: "option-not-applicable"`): `--split` and `--title` for a Markdown input, `--aliases` for a YAML input, `--signals` for a `.pptx` input, `--schema-comment` for a YAML output, `--drop-unsupported` for a Markdown output, and the drawing and PowerPoint flags for those outputs. The format of every file is checked against its name, so a `.png` output is never written as SVG (the `render --out deck.png` class of bug). A part the Markdown dialect has no syntax for is a `markdown/embedded` (or `markdown/dropped`) warning, as `to-md --fail-on warning` treated it.
    - **One output convention.** A command that writes a deck takes an optional output after its inputs and writes stdout without one; `-i`/`--in-place` rewrites the input (`edit`, `format`, `merge` (ours), `paginate`, `embed`, and `ingest` for its `--into` deck); `format --check`, `embed --check` (exit 1 when something would be embedded) and `paginate --check` (exit 1 on overflow) write nothing. `--output`, `--out`, `--out-dir`, `--name` and `--dry-run` are removed. `opf fill`'s data is always its second argument, whatever its name (`-` reads stdin; `--data` is removed), and its optional third argument is the output, a deck name or a file name pattern: `opf fill t.opf.md clients.csv decks/qbr-{client}.opf.md` (`{n}` the record number, `{column}` a slug of its value); `--combine` writes one deck. An existing output is refused before any warning is printed.
    - **Flag meanings.** `--format` is only a report format (`json`, `text`, `github` for validate, `patch` for diff). `--from` and `--to` name deck forms and replace `--input-format` and every deck `--format`. `--data-format csv|tsv|json` names the data of `fill` and `ingest` (their `--format csv|tsv|json`). ## 0.11.0 (2026-10-06)

- RR-54 (additive schema plus one behaviour change; lockstep with the renderer, PPTX and editor later): chart and table data. Contract: [docs/chart-table-data.md](docs/chart-table-data.md).
    - **Behaviour change (strict chart numbers):** core `chartNumber` is the one rule for chart values: a finite number, or a trimmed string in strict decimal syntax (`"12"`, `"-3.5"`, `"1e6"`). Anything else (`"12%"`, `"$5"`, `"(5)"`, `"1,234"`, `"Q1"`, booleans) is a gap and a `chart-value-not-numeric` validator warning, never a guessed value. Once the renderer and PPTX adopt it, a deck whose chart cells hold `"12%"` or `"$5"` previews and exports a gap where the exporter used to strip the characters and write 12 or 5. Data import (`createDataContent`, `opf import-data`) already used this rule and now calls `chartNumber`.
    - **Schema:** `NumberFormat` (the `NumberVariable.format` syntax, now shared by it); `DataColumn` (`{ name, format }`) wherever a chart, dataset or table column is a string; `StyledTableCell.format` (a body cell's own format wins over its column's); `ChartData.source` and `Dataset.source` provenance (`DataSourceRef`: `src`, `sheet`, `range`, `fields`, `retrieved`, `description`), which engines never read; top-level `datasets` with `{ "dataset": "<id>", "fields"? }` as the third `chart.data` branch and as a dataset-backed table form (`dataset`, `fields`, no `rows`/`columns`); `chart.mapping` (`category`, `x`, `series` by column name). A document that uses none of them validates as before; `pnpm check:breaking` reports none.
    - **Core API** (`@openpresentation/opf` and `@openpresentation/opf/data`): `chartNumber`, `formatDataNumber`, `numberFormatError`, `excelNumberFormat` and `numberFormatFromExcel` (round-trip every NumberFormat through an Excel format code; literal text is quoted as one run, so `0.0 m/s` is written `0.0 "m/s"` and never leaves `/`, Excel's fraction bar, bare), `inlineDatasets`, `inlineTableData`, `inlineChartData`, `resolveChartData` (the positional `[category, (x,) ...series]` table after datasets, fields and mapping, with `hasX`; an XY chart has an X column only with three or more columns, as both engines plot today), `resolveTableData`, `tableCellDisplayValue`, `datasetDiagnostics`, `unusedDatasets`, `isXYChartType`, `isDatasetRef`, and the `DataDiagnostic` and data types.
    - **Migration help:** `suggestChartNumberFix(chart, document?, { path?, column? })` returns, for a chart value column whose text cells share one display style (`"12%"`, `"$1,234"`, `"1,234.5"`), the JSON Patch that stores the numbers and gives the column the NumberFormat that shows the same text; lint attaches it as `fixes` to each `opf/chart-value-not-numeric` warning of that column (`LintDiagnostic.fixes`, the audit fix shape). Mixed styles, `(5)`, `1.234,5` and anything the format would show differently get no fix.
    - **Validation and lint:** errors `dataset-unknown`, `dataset-field-unknown`, `data-column-duplicate`, `chart-mapping-unknown-column` and `number-format-invalid`; warnings `chart-value-not-numeric`, `chart-data-source-unresolved` (a `ChartDataSource`, which no engine loads, [opf#240](https://github.com/OpenPresentation/opf/issues/240) descoped) and `chart-mapping-adapted`; lint keeps them as `opf/<code>` and adds the warning `opf/unused-dataset`. The bundled examples that show the `ChartDataSource` form keep it and carry the new advisory.
    - **Core integration:** `composeSlide`, `layoutTable` (which measures formatted cell text and reports it as the cell `value`) and pagination accept dataset-backed tables and charts; conversions, Markdown, format, diff and the audit keep or read the new fields; `resolveVariables` fills dataset rows.
    - **CLI:** `opf import-data --dataset <id>` writes the imported data into `datasets.<id>` (with the file as its `source`; a re-import keeps the format of each column whose name is unchanged) and references it from the new table or chart.
