# Changelog

## Unreleased

- RR-29: exported chart series keep distinct colours on dark and mid-tone cards (needs the core release with `chartPaletteForFill`, opf#270; raise the core floor with it). The exporter clamped each of the 12 series colours for 3:1 contrast on its own, so on a dark card the default palette's two dark blues were written as nearly the same colour (`5591B8` and `6E8FA5`, 4 lightness points apart on `334155`) and two series looked alike in PowerPoint. `chartColors` (and the chartex palette) now come from `chartPaletteForFill(panelFill, palette)`, the one function opf-render draws the preview with: colours that already pass 3:1 are unchanged, a colour the card moves is placed again at the nearest lightness that keeps its hue, 3:1 contrast, an 11 L* step from its neighbours and a colour difference from every other series (`77B6ED` and `A8D3FD` on `334155`). Only chart series colours change (and the shades derived from them): of the 101 bundled example decks that export without their external assets (the other 25 name image files the repository does not ship), 25 decks change 45 `ppt/charts/chart*.xml` parts, `srgbClr` values only (`test/fixtures/chartex-fallback-main.json` is regenerated for that reason, verified part by part: only chart parts differ and with their `srgbClr` values masked they are identical to the previous entries). Core's promoted-region reading order (regions composed left to right, top to bottom instead of alphabetically, opf#270) changes the order of the shapes on promoted-region slides and no geometry (34 slides of those 101 decks: the same shapes at the same positions, in a different order, with the `rIdOpfText` provenance relationship numbers following the new order): PowerPoint's selection pane and reading order now follow the visual order (55 example slides in 50 decks reported `audit/reading-order` before and none do now). The exporter writes shapes in core's item order and sorts nothing itself.

- Fix (RR-16, output-changing with the coordinated core, lockstep release): chart text is written at the size the preview draws on the 0.01 pt grid core now composes on ([opf#213](https://github.com/OpenPresentation/opf/issues/213)). `chartTextSize` rounded `max(14, minFontSize) * scale * 75` to the nearest hundredth of a point, but the preview draws the readability floor rounded up (core `snapFontSizeUp`) and an unfloored 14 px request rounded down; the two differed by 0.01 pt on slide sizes whose scale is not a whole number (A4 wrote 13.23 pt where the preview draws 13.24 pt). The run sizes of text boxes are unchanged in code: they come from core fits, which are now whole hundredths of a point, so `sz` equals the preview's size exactly. The chart text size test gains two A4 settings. No dependency range changes here; the core floor rises with the lockstep release.

- FF-45 (RR-17): native OMML equations are imported, not dropped. A paragraph whose content is an `mc:AlternateContent` with an `a14:m` math zone (`m:oMathPara`) used to import as empty text, because the readers took only the paragraph's direct `a:r` and `a:fld` runs. Both readers (`readParagraphs` and the ordered `nativeShapeParagraphs`) now read the `mc:Fallback` runs as the paragraph's text and, when there are none, the equation's `m:t` text in document order; the paragraph records the zones and import reports `math-equation-flattened` (`slides.N`, one per native shape) because OPF has no equation model and the equation's layout (fractions, radicals, limits, matrices) is not represented. Export is unchanged and now tested: a Cambria Math or Segoe UI Emoji scheme writes the chosen family and the authors' characters (ZWJ sequences, flags, keycaps, variation selectors, tag characters, math alphanumerics) byte for byte, whatever face the preview substitutes. Tests in `test/math-emoji.mjs`.

- Round trip (RR-09): rich text with hard line breaks (a newline inside a run, a blank line, a break between differently styled runs) re-imports as the one authored payload instead of separate blocks with `content-structure-changed`. The slide record already counted the native line shapes of a wrapped rich-text payload (`lines`); a payload with a hard break now stores `wrap: {lines, gaps}` instead (an older importer ignores it and keeps the flat blocks), where `gaps` holds the whitespace each line break deleted (`''` for a soft wrap, otherwise the newline, blank lines or trimmed spaces the break held, optionally split between the two runs at the break), never a word, and import rejoins the current native lines with exactly those separators. A payload whose runs cannot be proven to rebuild (a differently styled run inside the break, whitespace outside the lines, a changed character) stays unmarked and keeps its flat blocks and diagnostic; decks exported before this import as before. Hard breaks inside list items are recorded too (`OPF_SLIDE_V1.lists`, whitespace per list line number): the newline of an item or description returns, a blank line no longer becomes an empty description, a recorded break that no longer applies reports `list-line-break-changed`, and a break the export cannot account for exactly is reported as `document-provenance-omitted`; plain PPTX still joins continuation lines (it cannot tell a wrap from a break).

- Import details (RR-08): `fromPptx` returns what the PPTX can still prove. (1) `author`: an array author returns as the array (`OPF_DOCUMENT_V1` stores it; a plain PPTX splits only an exact `; ` list, the join the exporter writes), and the default creator `OpenPresentation` is no longer imported as an author when no author was authored. (2) Run colours that named a ColorRef (`var:`, a colour-scheme slot, a role) return as the name (`OPF_SLIDE_V1.colors`, names only, applied while the name still resolves to the run's colour in the imported document); in plain PPTX a run painted with a bare theme slot (`a:schemeClr`) returns as its slot name where the document's colour scheme holds that colour. (3) List item descriptions come back as `description` in root, group, region and plain decks (covered by test). (4) A `bullets` list keeps its key in blocks, groups and regions (`bullets: true` on the stored leaf; `type: 'text'` returns as authored). The chart null cells, scheme hyperlink slots and picture alt rows of the spec coverage report were already fixed (`test/import-fabrications.mjs`). Export output is byte-identical outside the OPF tags on the 126-deck example corpus.
- RR-32: template variables. `toPptx` accepts `variables` (values keyed by variable id) and resolves a deck that uses content variables, or is marked `template: true`, with core `resolveVariables` before exporting, so a template plus values exports the same bytes as the equivalent hand-written deck (`test/template-variables.mjs`, with and without provenance). A template exports with each unfilled variable's `example` (diagnostic `variable-example-used`); a normal deck with an unfilled required variable throws `OPFPptxError` `unfilled-variables`; a bad value throws `invalid-variables`. The package stores the resolved deck, not the template form, so `fromPptx` returns the filled deck (template provenance is a follow-up). Decks without content variables are untouched. Needs the core release that ships `resolveVariables`; an older core ignores the option.

## 0.11.9

- Release 0.11.9 (patch number with an output change and additive API; four changes since 0.11.8, `git log opf-pptx-v0.11.8..main` is #129, #130, #131 and #136; no API removed, no dependency range changed: the core floor stays `@openpresentation/opf` ^0.11.4, the optional renderer peer ^0.11.0 and the development renderer 0.11.9). **Output change (#131, RR-11):** a deck with a footer slide number, date or text now exports them as native PowerPoint Header & Footer placeholders (`ftr`, `dt`, `sldNum` on the slide, master and layout, with `p:hf` flags) instead of plain tagged shapes, so Insert > Header & Footer shows the right state, Apply to All works and slide numbers renumber after a reorder; the shapes keep the same names, boxes, runs, fields and `OPF_FURNITURE_V1` tags, so preview and export geometry agree, and every export now also carries the three footer placeholders on its slide master, layout and notes master (#136), so a deck with no footer differs from 0.11.8 only in those three parts (and a non-English deck's placeholders carry its language), and Insert > Header & Footer works on footer-less decks. Import reads native footer placeholders with or without tags (additive). **Output change (#130, RR-10):** an SVG image is now a native SVG picture, as PowerPoint 2016 and Microsoft 365 store it (a `p:pic` whose `a:blip` embeds a PNG fallback and carries the `asvg:svgBlip` extension over the SVG media part), instead of the "Image unavailable" placeholder (0.11.7 and 0.11.8 degraded every SVG to it); `fromPptx` returns the SVG for such a picture. The PNG fallback is drawn in Node by `@openpresentation/opf-render` (the optional peer, ^0.11.0; loaded lazily and only when an SVG is exported) or by `options.svgRasterizer`; with neither (and in a browser build without a rasterizer) the SVG still exports as the unavailable-image placeholder with an `unresolved-asset` diagnostic of reason `svg-rasterizer-unavailable` (`strictAssets` throws it). An SVG is sanitized before it is embedded. Decks with no SVG image are byte-identical in this respect. **New opt-in API (#129, RR-13):** `fromPptx(bytes, {signals: true})` resolves to `{document, signals}` with the raw, deterministic, size-bounded per-shape facts of every slide, for hosts that classify structure in decks without OPF provenance; `fromPptx(bytes)` and the document returned with the option on are exactly the 0.11.8 import output. New exports `DEFAULT_SIGNAL_LIMITS`, `SIGNALS_VERSION`, `isMonospaceFamily` and the `PptxSignals` types. Descriptions follow.

- RR-11: native PowerPoint Header & Footer objects (output-changing for decks with a footer; import additive). The first footer text, date and slide number that fit one accepted line are now real placeholders on the slide (`p:ph type="ftr|dt|sldNum"`, layout idx 11/10/12) instead of plain shapes: same name (`OPF furniture N part K line 0`), same explicit `a:xfrm` core composed, same runs and live `slidenum`/`datetime1`-`datetime7` fields, same `OPF_FURNITURE_V1` tag, so preview and export geometry agree. The slide master (idx 4/2/3) and layout carry the three placeholders at the first slide's boxes (core's default footer band for a type no slide uses) with `p:hf hdr="0"` and `sldNum`/`ftr`/`dt` on when a slide uses them, so Insert > Header & Footer shows the right state and Apply to All works; the notes master gets `<p:hf hdr="0" ftr="0" dt="0"/>`. Header parts, organization, section, socials, images, second text/date/number parts and multi-line footer text stay tagged shapes. The footer manifest marks a native part with `ph` (older importers ignore it and read the same tags). `fromPptx` reads `dt`/`ftr`/`sldNum` placeholders with or without tags (zone from the placeholder's position, resolved through the layout and master), treats a placeholder PowerPoint's dialog removed as intent, merges a placeholder added in PowerPoint into the slide's footer, and promotes the footer most slides share to `design.footer` with `design.footer: false` on slides that lack it. A deck with no native footer part is byte-identical to the previous export. New `docs/native-header-footer.md` (mapping, dialog-edit table, vetoable decisions) and `test/native-furniture.mjs`. PowerPoint opening and editing of the new objects is the supervisor's native check (`scratchpad/rr-11-native/manifest.json`).

- RR-11 follow-up (output-changing, master/layout/notes-master parts only): every deck now carries the `dt`/`ftr`/`sldNum` placeholders (layout idx 10/11/12, master idx 2/3/4) and `p:hf` flags on its slide master and layout, and `<p:hf hdr="0" ftr="0" dt="0"/>` on its notes master, not only decks with a native footer part; with no slide using one the flags are 0, so Insert > Header & Footer works on a deck with no footer and Apply to All creates the placeholders at core's default footer band. The placeholders now carry the deck language (`lang`) like every other part (the first RR-11 change left `en-US` on them in a non-English deck). Slides, tags, charts, the theme and all geometry are unchanged. Over the 126 bundled examples against the previous output: 43 decks gain the placeholders (+3,043 bytes uncompressed per deck across the three parts), 58 decks change only the placeholders' `lang`, 25 are byte-identical, and no part other than the slide master, layout and notes master changes. The chartex fallback byte fixture (`test/fixtures/chartex-fallback-main.json`) is regenerated for that reason, verified part by part: only those three parts differ, diagnostics are unchanged.

- Native SVG pictures (RR-10, output-changing for decks with an SVG image; import additive): an SVG image (content image blocks, root `image`, `design.slideImage`, `design.watermark`, header and footer images and logos, cover and section logos) exports as a native SVG picture: a `p:pic` whose `a:blip` embeds a PNG fallback and carries `a:extLst/a:ext uri="{96DAC541-7B7A-43D3-8B79-37D633B846F1}"/asvg:svgBlip` over an `image/svg+xml` media part, with the `svg` content type registered. A picture bullet (`a:buBlip`) and an image background use the PNG raster; a duotone recolor or a non-rectangular mask keeps the PNG with `svg-image-rasterized`. The size comes from the SVG's `width`/`height`, else its `viewBox`; fit, crop and contain use the raster path unchanged. The PNG fallback is rasterized at 192 dpi of the displayed size (long side a multiple of 128 px, 128 to 2304) by `options.svgRasterizer(svg, {width, height, scale, text})`, whose Node default is opf-render's `svgToPng` (optional peer, loaded lazily; nothing in the browser bundle); identical SVG and PNG parts dedupe. With no rasterizer and no opf-render the SVG exports as the unavailable-image placeholder with `unresolved-asset` reason `svg-rasterizer-unavailable`. An SVG is validated as XML and sanitized before it is embedded and on import (`<script>`, `<foreignObject>`, event handlers, link animations, every `href`/`url()` other than `#fragment` or an inline raster, `@import`, `xml-stylesheet`, DOCTYPE; a safe SVG is embedded byte for byte, otherwise the sanitized serialization with `svg-sanitized`); nothing is fetched or executed. Only a source typed `image/svg+xml` is an SVG. Failures keep the placeholder with `unresolved-asset` reasons `svg-malformed`, `svg-no-size`, `svg-too-large` (over 8 MiB), `svg-unsafe`, `svg-unreadable` and `svg-render-failed`; strict mode codes for SVG are `invalid-svg-image`, `svg-rasterizer-unavailable` and `svg-render-failed` (0.11.7 and 0.11.8 threw `unsupported-image-dimensions`). PowerPoint saves an SVG picture without the PNG fallback; import takes the SVG alone, the slide-image, watermark and logo identities ignore whitespace and compare a canonical crop, and a picture whose provenance is invalid still imports as an ordinary SVG image with the diagnostic. `fromPptx` returns the SVG (`data:image/svg+xml;base64,...`) for a picture with `asvg:svgBlip`, from this exporter's files and from PowerPoint's; a damaged SVG part imports the PNG fallback with `invalid-svg-image`. A local `.svg` path is read in Node and `imageResolver` may return SVG bytes. The preview in opf-render 0.11.9 does not draw an SVG data URI yet (it draws the placeholder); the export frame equals the same-proportion PNG's. Tests in `test/svg-image.mjs`, `test/native-svg-decks.mjs` and `test/svg-image-degrade.mjs`.

- Import signals (RR-13, additive): `fromPptx(bytes, {signals: true})` resolves to `{document, signals}`, where `document` is exactly what `fromPptx(bytes)` returns and `signals` is a deterministic, JSON-serializable, size-bounded list of raw per-shape facts for every slide, so a host can reconstruct structure (code, metrics, quotes, timelines, regions) in decks that carry no OPF provenance with its own classifier. Per shape: kind (text, shape, placeholder, picture, media, table, chart, smartart, ole, group, connector, line), box in reference px and EMU with group transforms applied and layout/master placeholder boxes inherited, z-order, group nesting, rotation, flips, placeholder type/idx, text runs with the effective font family, size, weight, italic, colour (theme tokens resolved) and a monospace flag, paragraph level, bullet, alignment and spacing, fill, outline and geometry, picture, table and chart summaries, slide, layout and master names, and the OPF path each shape became (`slides.N.blocks.M`, `.title`, or the rebuilt group, region or root path of a tagged round trip). Limits (`maxSlides`, `maxShapesPerSlide`, `maxTotalShapes`, `maxTextCharsPerShape`, ...) bound the output and what they drop is counted. No network, model, clock or randomness; the default import output is unchanged (the option is off by default and the document is identical with it on). New module `src/import-signals.js`, new exports `DEFAULT_SIGNAL_LIMITS`, `SIGNALS_VERSION`, `isMonospaceFamily` and the `PptxSignals` types; `rebuildContent` also returns where each flat block landed and restore groups record whether they were applied (internal). Tests in `test/import-signals.mjs` against a hand-written, untagged deck (`test/signals-deck.mjs`), a PptxGenJS deck and OPF exports.

Tabs, line endings and valid supplementary Unicode remain accepted; this does not certify glyph coverage.
- Export accepted code parts as editable native lines with explicit tab stops. Retain complete code source and metadata through guarded native shape tags, including soft-wrap boundaries and CR/LF/CRLF. Missing or ambiguous groups retain visible shapes with diagnostics. See [code round-trip scope](docs/code-roundtrip.md).
- Preserve significant whitespace, empty paragraphs, interleaved native fields and explicit line breaks during text import. Keep complete multiline titles rather than silently taking their first line. Grouped text is retained with a transform/reflow diagnostic.
- Add wide/portrait offline browser and actual Windows PowerPoint source/edit/save/reopen/import checks. Native geometry, styling, font theme and raster equivalence are not reconstructed by this source round-trip feature. Requires core 0.9.0 and renderer 0.7.0 for coordinated preview/font measurement.

## 0.2.0

This minor release requires Node 20.9 or later and OPF 0.4.1. Browser entrypoints remain available without native Node dependencies.

- Keep background-only and empty slides blank on import instead of adding a synthetic slide title.
- Add captured Keynote 14.4 native PNG/PPTX regression references for editable gradients, portrait opacity and native import; document the Quick Look thumbnail limitation separately from native viewer evidence.

- Preserve native dimension precision on import so standard-size canvases do not acquire small raster differences through rounded inch values.

- Restore native JPEG quarter-turns and mirrors into EXIF on import without recompressing pixels; preserve source JPEG bytes for this exporter's eight supported orientations.
- Add bounded EXIF insertion/update that retains existing metadata offsets and links, plus import diagnostics for unsupported crop, rotation and metadata cases.

- Preserve fixed solid/linear-gradient backgrounds as editable native fills, including opacity, stop colors, per-slide overrides and inline theme overrides.
- Convert gradient direction and stop intervals between SVG bounding-box and native slide coordinates, with regression coverage across landscape, portrait and square canvases.
- Import supported RGB solid/linear fills and expose path-specific diagnostics for native gradients outside the OPF representation. Keynote appearance is verified by captured native references; Microsoft PowerPoint remains unverified.

- Convert WebP to compatible static PNG pictures by default in Node and browser exports; preserve alpha, EXIF orientation and the first animation frame. Add imageFormat: "preserve" for original WebP embedding.
- Use lazily loaded Sharp 0.35.4 for local Node conversion and browser image/canvas APIs in browser bundles. Raise the Node minimum to 20.9.0. Conversion errors include the image path and enforce a 40-megapixel limit.
- Verify 36 cases against independent Pillow pixel references and 13 browser checks. Keynote 14.4 displays all six converted specimens, replacing its empty-rectangle WebP import.

- Detect PNG/JPEG/GIF/WebP content from embedded bytes, repair native media extensions/content types and import correct data-URI MIME types even when filenames or resolver hints disagree.

- Repair duplicate native object IDs on slides mixing tables with other objects, and sort normalized ZIP paths for stable multi-chart export bytes.

- Preserve headerless table data and empty rows on import. Export native header-row flags and honor explicit XML boolean flags when importing, including edits from other applications.

- Fit native table cell font sizes with the same loaded-font measurements and effective nested composition settings as the SVG preview.
- Match table alignment, line spacing, margins and theme border colors; pad uneven rows so every column remains present.
- Preserve original cell text and native editable tables. Natural wrapping still belongs to the PowerPoint viewer; native raster parity remains unverified.
- Compare 168 cells across two slide sizes, Roboto and Calibri substitution, headers, uneven rows and all text alignments. Twenty-four cases require shrinking.

- Preserve image proportions with centered native fit/crop matching presentation and slide imageFill settings.
- Measure embedded PNG/JPEG/GIF/WebP bytes without a second resolver call or an image-size dependency. Unreadable/unsupported dimensions produce a path-specific error.
- Translate all eight JPEG EXIF orientations into native rotation/mirroring while preserving compressed pixels and normalizing only the embedded orientation tag.
