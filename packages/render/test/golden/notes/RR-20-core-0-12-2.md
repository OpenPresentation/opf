# RR-20: the default baseline records the core 0.12.2 examples

Moved no hash. `opf-examples-png.cover-centering/_baseline.json` (the default baseline: the publish workflow and a bare `npm test`) changes only its `source.sha256`, from `d089278f...` (the examples of the published core 0.12.0) to `485b5c07...` (the examples of core 0.12.2, the floor since the 0.12.1 release prep, #126). No deck file changes: all 805 raster hashes are identical.

Why: core 0.12.1 moved 81 example decks to singular audience ids without moving a pixel (core opf#309, RR-41). Core's ecosystem lock carried that decision as a reviewed core copy of this baseline (`opf/scripts/fixtures/opf-examples-png.audience-ids.sha256.json`, same 805 hashes, new digest), but the publish workflow installs the registry core and always uses this repository's own default baseline, so the `opf-render-v0.12.1` publish run failed on "Golden corpus changed" ([run 37396674784](https://github.com/OpenPresentation/opf-render/actions/runs/37396674784)) and 0.12.1 was not published. The tag stays; 0.12.2 ships with this baseline.

How it was checked: with the installed registry core 0.12.2 (`npm ci`, as the publish workflow installs), `node test/golden.mjs` failed only on the source digest (`diff.json`: `sourceMatches: false`, 0 changed slides); the candidate equals the core fixture byte for byte (source, scale, format, font policy and all 805 entries). The commit itself is the regenerate-goldens output in the pinned Playwright image (core main of the lock, whose examples have the same digest as the published 0.12.2), and CI then runs the full suite against this baseline in that image. The comparison is unchanged: exact hashes at scale 0.25, no tolerance.

Follow-up (opf-render#130): ci.yml first selected this baseline through `golden-override`, but the roller makes that selection the lock's golden, and core main had already moved to the RR-20 example decks (digest `394c4ce7...`, core opf#367). The roll of 2026-10-06 ([run 37405529903](https://github.com/OpenPresentation/opf/actions/runs/37405529903)) then failed twice: `ecosystem-render` compared core main's examples with this baseline (`394c4ce7...` vs `485b5c07...`), and `ecosystem-core (registry)` lost the retained core golden (core selects it only while the lock's golden is in core), so the pinned renderer used its own `d089278f...` baseline for the installed core 0.12.1. ci.yml selects the lock's golden again (`golden-override: ''`): core's reviewed `scripts/fixtures/opf-examples-png.example-decks.sha256.json` (same 805 renderer hashes plus the 14 reviewed example-deck hashes) for core main, and the retained RR-41 copy for the published core. This file stays the default for the publish workflow and a bare `npm test`.
