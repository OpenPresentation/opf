# Raster regression baseline

## Layout, review notes and regeneration (RR-52)

Each baseline is a directory, `test/golden/<name>/`, holding `_baseline.json` (every manifest field except `entries`: version, source digest, format, scale, font policy) and one file per example deck, `<deck path without .opf.json>.sha256.json` (`{ "deck": ..., "entries": { "<deck>.opf.json#<slide>": { "sha256", "bytes" } } }`). `test/golden-store.mjs` reassembles the exact manifest the single file used to hold (`scripts/golden-migrate.mjs verify --ref <old-layout ref>` proves the migration byte-for-byte), so the comparison is unchanged: exact PNG hashes at the baseline's scale, no tolerance.

- **Selecting a baseline.** `OPF_GOLDEN_BASELINE` names the directory. A legacy `.../<name>.sha256.json` path that no longer exists as a file selects `.../<name>/`, and a legacy single-file manifest still loads, so older pins in this repository, core's `ecosystem-ci.yml`, opf-pptx and opf-editor keep working unchanged.
- **In CI (RR-50).** `ci.yml` selects no baseline by hand: the `ecosystem-refs` step exports `OPF_GOLDEN_BASELINE` from core's `ecosystem.lock.json` (`golden`, the baseline the locked core examples and renderer agree on), unless its `golden-override` input names a renderer directory (`opf-render/test/golden/<name>`). A pull request that moves pixels sets `golden-override` to its own directory; `regenerate-goldens` writes only into a renderer directory and says how to create one when the lock's golden lives in another checkout. The publish workflow and a bare `npm test` still use the default `opf-examples-png.cover-centering` (the published core examples).
- **Review notes.** Do not edit this README for a baseline change (every PR prepending a section here is what made two golden-moving PRs conflict). Write the note as `test/golden/notes/<ID>.md` (which decks moved, why, how they were reviewed) and in the PR description. The sections below are the history before RR-52.
- **Regenerating.** Do not hand-edit deck files and do not copy `candidate.json` over a baseline. Add the `regenerate-goldens` label to the pull request (or run the `regenerate-goldens` workflow on its branch). It runs only in the Playwright image `ci.yml` pins (it refuses any other runner), renders the corpus, rewrites only the deck files whose hashes differ, uploads `diff.json` and the review sheets of the changed slides as artifacts, pushes one commit, and dispatches CI on it. Review stays human: look at the changed slides in the artifact before approving. A merge conflict in deck files is resolved by merging `main`, taking either side, and regenerating.
- **Locally.** `npm run golden:update` writes a candidate (and with `OPF_GOLDEN_ARTIFACTS=changed`, only the changed slides) under `artifacts/golden/`; `npm run golden:promote` writes the changed decks into the selected baseline and `artifacts/golden/diff.json`. Hashes from a machine that is not the pinned image are not comparable; only the workflow's output is committed.
- **What is not changed.** The comparison (exact hashes, no tolerance), the 0.1 px reference-font gate and the 0.15 px variable-font gate. `golden-promote` refuses a different version, format, scale or font policy.

## RR-16: composed font sizes on PowerPoint's 0.01 pt grid (core after 0.11.4)

Core now composes every font size as a whole multiple of 0.01 pt (1/75 px; opf#213), so the preview draws the size the PPTX writes (`sz` is hundredths of a point) instead of a fractional size such as 14.145 pt. `opf-examples-png.cover-centering.sha256.json` (the CI and default baseline) is regenerated: 316 of 805 slides change against the previous baseline, with an unchanged source digest, and the other 489 hashes are unchanged (the manifest is replaced as a whole, but only those 316 entries differ; the diff shows no other line). Every one of the 316 is a size or position consequence of the snap and nothing else. A slide's rendered SVG differs in 318 slides (2 more than the 316 raster hashes: their changes are under a pixel at golden scale 0.25) and never in element count; in 303 of the 318 every text size moves by at most 0.018 px (a grid step is 0.0133 px) and the rest of the slide by at most 0.13 px, because baselines and line boxes accumulate the size change down a text block. In the other 15 (slide 6 of 15 gallery decks: 7 `number-4x`, 6 `number-6x` and 2 `number-1x` metric slides) the metric layout search picks a neighbouring candidate when a trial's fit flips by a sub-pixel amount: the value and label sizes trade up to 2.2 px, with the same total font reduction and no new overflow; boxes move by at most 0.1 px. The same environment (Windows, Node 26.4.0, scale 0.25, `systemFonts: false`) first reproduced the previous baseline byte-for-byte against the base core, then produced the 316 against the core that carries the change (opf `RR-16` branch); CI (Linux Playwright container) confirms the hashes on the PR, which pins that core commit in `.github/workflows/ci.yml`. The pin moves to the merged core commit, and the renderer's core floor rises with the lockstep release; no renderer source changes. `docs/programs/release-readiness/rr-16-font-size-grid.md` in opf has the rule and the measurements.

## September 7 review

Known limitations include unresolved media placeholders, limited advanced chart families, low-contrast combinations in some source presets, sparse layout/density choices, language shaping and native PowerPoint parity.
