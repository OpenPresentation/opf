## 0.34.0 (2026-11-13)

- RR-107: each GitHub release includes the full-font Claude Desktop extension `opf-<version>.mcpb`, checked by starting its server, and its SHA-256 file. Bundle font resolution also works with native Windows paths.
- RR-111: the OPF viewer registers three MCP Apps app tools, so a host that calls tools in a view (Claude, with a remote connector) lets the model work on the deck that is already open: `read_deck` (revision, name, outline, selected slide and check findings, and the source in JSON, YAML or Markdown in pages under the 100,000-character result limit, each with a `textHash`), `select_slide` (by index or id) and `edit_deck` (1 to 100 JSON Patch operations with a required `expectedRevision`, applied as one undoable edit). `edit_deck` changes nothing on a stale revision, while the user is typing, over an invalid source draft, for an operation on the whole deck or the whole `/slides` array, for more than 200,000 characters of operations, or for an edit that would make the deck invalid. Mistakes in the arguments come back as results that say how to fix them. In the source pane JSON keeps its formatting; YAML and Markdown are written again from the deck (YAML comments are dropped, and the pane says so). Hosts without app tools keep the context updates and Send.
- RR-111: `open_editor` ("OPF deck editor"), a direct entry point to the OPF viewer's editor (`_meta["openai/ui"].entrypoints: [{ "type": "global" }]` beside `_meta.ui.resourceUri`). Called with `{}` it opens a two-slide starter deck the user can edit at once; the start row opens a bundled example or pastes a deck (Paste selects the whole source and focuses it, and reads the clipboard where the host allows it); `example` and `title` are optional, and a title given with an example renames it. The model's first context names what opened and carries the deck. `show_deck`'s contract is unchanged apart from an optional `session` input and a `viewer` key in its result.
- RR-111: the `ui://opf/deck` content item now asks for the side panel (`_meta.ui.preferredDisplayMode: "fullscreen"`; the host decides). The viewer lays out by the container the host reports (`containerDimensions`, down to 320px wide) and fills the frame in full screen also when the host sends no dimensions, pads itself with the host's `safeAreaInsets`, and at the narrowest size gives every control at least 44 by 44 CSS pixels and wraps long status messages, which clear themselves after a few seconds. Its Expand control asks for the larger view from the click itself, says so when the host keeps the viewer where it is, and offers the way back to the conversation. The bundle carries only zod's English messages (a build rule that fails when it no longer applies), which keeps the viewer under the JSON-RPC frame limit.
- RR-111: the MCP viewer (`show_deck`, `open_editor`) draws a deck's set icons (`"icon": "lucide:rocket"`). It cannot fetch, so it reads them from its server through a new app-only tool `read_icons` (`{ set, names, index? }`, at most 100 icons a call, each set's index with its license and copyright once), offered when the server has icon sets and the viewer; `show_deck` and `open_editor` name the sets in `iconSets`. The viewer's checks and the checks in `read_deck` and `edit_deck` results wait for the deck's icons, so they report icons as `validate_deck` does (an unknown name with its nearest names); a load that cannot happen draws the slide without the icon and says why. `opf-mcp` and the `.mcpb` read the installed icon files; a Worker passes `sources.iconSets` over the icon files it serves (docs/mcp.md). The page carries no icon data. `search_icons` no longer describes an empty list of sets on a server without icon sets.
- FA-37 (breaking): layout words that follow the deck's direction are `start` and `end` instead of `left` and `right`; this package reads and writes the new words. Rename them in your decks; validation suggests the new word, and the core changelog lists every place.
- The OPF viewer (`show_deck`) is redrawn to the openpresentation.org design system:
    - In a client that sends the standard MCP Apps style variables, surfaces, text, borders and fonts follow the client (light and dark); the accent and status colors stay OPF colors.
    - A 48px bar (Undo, Redo, view switch, Design, Find, full screen, Send; Send is filled only while there are unsent edits) and a 28px status footer (the verdict, which opens the Review panel when there are issues; the slide navigator; where the edits are; the version). Inline, the view is as tall as the slide needs; below 860px, Both stacks the slide over the source. The thumbnail strip keeps the open slide in view, and a slide-shaped placeholder shows until the deck is drawn.
    - Undo stops at the deck as opened. The source pane Copy works without the clipboard permission; Download and the editor Export menu (PowerPoint, PDF, SVG and PNG slides, OPF source, made on the user machine) show only where the client saves files (`ui/download-file`). The viewer page grows from about 8.5 to 10 MB (2.8 MB compressed).
    - `@openpresentation/opf-render/export-browser`: `toPng` and `toPdf` take `svgSource: "data"`, which hands the SVG to the browser as a `data:` URL for a page whose Content-Security-Policy allows no `blob:` image; a `blob:` URL that does not load is retried as `data:`.
    - `show_deck` asks the model to leave `view` and `slide` out unless the user asked for the source or one slide.
- RR-111: core precompiled validators (the `worker`, `workerd` and `edge-light` engine and `@openpresentation/opf/precompiled`) are about 900 KB smaller, with the same errors as the Ajv runtime build; the Node and browser entries do not change. The MCP viewer (`ui://opf/deck`) shrinks by the same amount and stays about 1 MB under the 10 MiB stdio frame limit.
- RR-63 (breaking for hosts that register the gallery icon sets): a host now loads only the icons its decks draw. In 0.33 `galleryIconSets` loaded whole sets as modules, so every server bundle carried Lucide and Tabler. Decks do not change.
    - The icon data is static files in `@openpresentation/gallery`, exported as `@openpresentation/gallery/icons/*` (`<set>.json` index, `<set>/<name>.json` per icon, `<set>.icons.json` whole set, `<set>.tags.json` search keywords). `galleryIconSets` is now a function: `galleryIconSets()` reads the installed files in Node, Bun and Deno; `galleryIconSets(load)` reads through `load(path)`; `fetchIcons(baseUrl, fetcher?)` is the `load` for files a host serves (a fetch function or a binding such as `env.ASSETS`); `galleryIconSets({ lucide })` registers whole sets a server imported. `installedIconSets()` is `galleryIconSets()` where the files can be read and undefined elsewhere. The `@openpresentation/gallery/icon-sets/<id>` modules are removed, and `Catalog.iconSets` takes `IconSetLoader` functions.
    - Loaders are called with `{ icons: [names] }` (a search asks `{ tags: true }`); a loader that resolves with the whole record still works. An icon that cannot be loaded never blocks drawing: `ensureIcons` does not reject, the slide draws without the icon, and `opf/icon-unknown` says which icon and why; `ensureIcons(deck, { catalogs, retry: true })` asks again. A bundled Node server (ESM or CommonJS) deployed with its `node_modules` draws icons with no setup, and a CommonJS bundle of core's Node build no longer fails to load the engines.
    - Core's Node defaults, the CLI and the stdio MCP server register `galleryIconSets()`, so `convert`, `open`, `opf convert`, `opf validate` and the MCP draw and check icons with no setup, and their bundles carry no icon data. In a Worker, `@openpresentation/mcp`'s `defaultSources()` registers no icon set; pass `sources.iconSets`.
    - Editor: `await loadIconSets(editor)` still loads the deck's icons; `setIcon` returns `ready`, which a headless host awaits before `composeSlide`. `loadIconSets(source, ids, { icons, tags })` loads only the icons asked for, `searchIcons` reports `unavailable` sets and rejects with `icon-sets-unavailable` when none could be read, and the picker shows why instead of "no matches".
    - A browser page writes `galleryIconSets(fetchIcons("/opf-icons/"))`, a Worker `galleryIconSets(fetchIcons(new URL("/opf-icons/", request.url), env.ASSETS))`, with `node_modules/@openpresentation/gallery/dist/icons/` copied to `/opf-icons/` by its build. See docs/icons.md, "Loading", and docs/migrations/0.34.md.

Preserve editor, rendering, diagrams and all Export formats while excluding unreachable native-import code from the browser page. Refuse an oversized JSON-RPC resource during build, including JSON escaping and metadata.
- RR-111: viewer downloads and messages follow Claude MCP Apps rules. A download file name is the last segment of the URI as written, one request runs at a time with a ten-minute timeout, and a host without downloads gets "This host does not offer downloads here" and the copy fallback. Send to Claude handles a refused or unconfirmed message and stays usable to retry. - Preserve exact-source and guarded host downloads alongside the redesigned MCP viewer and Export menu. Suggested filenames are URI-encoded, denied or failed host requests remain visible, and source/Export downloads share one transport without an iframe download fallback.

- The guides, agent skills and package READMEs describe Mermaid, Graphviz DOT and PlantUML diagrams and their native-shape export consistently; video references are documented as linked placeholders, and LibreOffice support stays experimental.

## 0.33.0 (2026-11-08)

- LH-14: icons. An optional `icon` on a list entry (`items[].icon`), a metric (`metric.icon`) and a group (`icon` on a block with `blocks`) draws an icon on a chip, as Claude Design draws a feature list or a "what we will cover" card: in the marker column of a list (in place of the bullet, and of an agenda's numbered badges), above a metric, at the top start of a group. The value is `"<set>:<name>"` (`"lucide:truck"`), a bare name from the deck's new top-level `icons` map (an author's or an LLM's own SVG, written once), or an SVG source (`asset:<id>`, a relative path, an HTTPS URL or a data URI). Icon sets are a new catalog kind (`spec/schemas/icon-set.schema.json`, `catalogs.<group>.iconSets`): `@openpresentation/gallery` bundles Lucide (ISC, `lucide-static` 1.68.0) as the default set and Tabler outline (MIT, `@tabler/icons` 3.50.0), generated by `scripts/build-icon-sets.mjs`, with their licenses in each record and in the new `THIRD-PARTY-NOTICES.md`; the new entry `@openpresentation/gallery/icon-sets` exports `galleryIconSets`, a catalog to register beside `gallery` (`catalogs: [gallery, galleryIconSets]`) whose loaders import each set (`@openpresentation/gallery/icon-sets/<id>`) only when a deck uses it, so `gallery` itself carries no icon data; `ensureIcons(deck, { catalogs })` (core) loads what a deck names before the synchronous code reads it (`toPptx`, the renderer's browser `ensure`, core's `convert`, `opf validate` and the MCP call it; core's Node defaults, the CLI and the MCP register `galleryIconSets`). An SVG is read, never run: one paint makes a recolorable glyph (path commands in a 24 unit box), several a picture with its own colors; a script, event handler, external reference or raster refuses it. The chip is a light tint of the primary with the glyph in the primary (the inverse on a dark slide); it is a guarded drawing rule of composition (`icons` with compact chips a line high, `icon-chips` with chips 1.75 em across), so an icon never sets text smaller: a slide without room draws no chips. The preview draws SVG paths; the PowerPoint export draws a native ellipse and editable custom geometries in the theme's accent (`a:schemeClr val="accent1"`, the chip with lumMod/lumOff), so the icon recolors with the theme, and a multicolor icon as an SVG picture with its PNG fallback; import gives each `icon` back (OPF_ICON_V1 tags; the `icons` map travels in the document provenance). New findings `opf/icon-unknown` (with the nearest names), `opf/icon-invalid` and `opf/icon-dropped`; the MCP has a `search_icons` tool. New core exports: `ensureIcons`, `resolveIcon`, `parseIconReference`, `embedIcons`, `iconColors`, `iconFromSvg`, `iconPathCommands`, `iconPathData`, `placeIconCommands` (`/composition`), `SlideComposition.icons` and `ListEntryLayout.icon`. See docs/icons.md. Slides without icons compose and draw as before.
- LH-158 (output-changing for covers and sections over a measured picture background): the heading group of a sized title area (a cover, a section) goes where the picture lets it read. Its candidates are the top, middle and bottom of the area, at the layout's side alignment or centered, across the area or in a narrower column (60% or 70% of the slide) where the group keeps its sizes; the automatic scrim at the place that needs the least of it; and a panel, the group in a start-side column of 40% (or 50%) of the slide on the slide's background color with the picture bleeding on the rest. Core scores each on the host's measured grid (`pictureLuminance`) under the group's ink and the scrim's margin, seen through the author's overlay: the gray spread, the contrast of the text color without a scrim, and the host's new optional `busy` and `salient` weight grids (from any vision model). It keeps the layout's own place when it reads, else takes the best place that reads, else the place the scrim carries with the least opacity, else (when that scrim would be above 50%) the panel; an `overlay` key leaves no scrim and no panel. `SlideComposition.pictureText` reports the choice and every candidate with its score; `scorePictureText` and `choosePictureText` are exported. The new `textPlacement` key of an image background (`top-start` to `bottom-center`, or `panel`) picks a place outright, and the editor's background panel has a Text placement control for it. Without a measurement a low group is centered as before. Both engines draw the panel as an opaque scrim (`form: "panel"`), one native rectangle in PowerPoint. On the narrative corpus n01, n02 and n07 move to the calm top of their pictures; nothing else in the corpora moves.
- The OPF viewer as an MCP App (SEP-1865). The new tool `show_deck` opens a deck inside a client that supports MCP Apps, such as Claude on the web and desktop, with the playground's three views: Preview (the slides), Source (the deck's JSON, YAML or Markdown, checked as you type) and Both. The view is one HTML page, the resource `ui://opf/deck` (`DECK_APP_HTML`), that bundles the editor, the renderer and core's precompiled validators. It runs in the client's sandbox with no network, no eval and no WASM, so all deck work happens on the user's machine. When the user edits, the whole deck goes back to the model as context; a Send to Claude button also starts a turn. `show_deck` also checks the deck and answers in text for clients without MCP Apps. Fonts other than the built-in Roboto come from `opf-mcp` through the app-only tool `read_font_file`, which serves the installed renderer's files in 512 KiB pieces; the renderer checks each file's SHA-256 before using it. A hosted server can pass `processDecks: false` so it does no deck work: `show_deck` then only opens the view, which checks the deck and sends the findings to the model, and `validate_deck`, `convert` and the `fix_validation_findings` prompt are left out. `createOpfServer({ deckApp: false })` leaves the view out. The viewer has the editor's Undo and Redo, review pill and Review panel, Design menu, and Find and replace. The server also builds as a Claude Desktop extension (`pnpm --filter @openpresentation/mcp run build:mcpb`, `opf-<version>.mcpb`). The extension carries the renderer and its fonts and needs no Node install or configuration; `--no-script-fonts` builds a lite bundle without the script faces. For a hosted server, `siteFontFiles({ fetch })` serves the viewer's fonts from a site that already serves the OPF preview fonts (the OpenPresentation site's `/opf-fonts/` layout), in a Worker through its static-assets binding, and `deckApp.html` can be a function, so a hosted server loads the viewer's page only when a client opens it.
- SH-04: overlay shapes and connectors. A slide's `shapes` array is drawn over the composed slide, above the content and the furniture, in array order, and never moves content. An overlay shape has the shape block vocabulary (preset or `path`, `adjust`, fill, stroke, style, the effects, `rotate`, `flip`, text with `anchor`, `padding` and `textDirection`, `alt`, `decorative`, `hidden`, `link`) and one placement: `x`, `y`, `width` and `height` (fractions of the slide; `x` from the right edge in a right-to-left deck) or `at: { block, edge, offset, width, height }` against a composed block (`top`, `bottom`, `start`, `end` or `center`), so it follows the block; `layer: "back"` draws it behind the content (above the background and watermark). A connector (`{ connector: { from, to, route, fromSite, toSite }, stroke }`) joins two blocks or overlay shapes at connection sites (a preset's own, a rectangle's four for any other block), chosen automatically as the facing pair with the shortest route; `route` is `straight`, `elbow` or `curved`. A connector's `adjust` (`adj1`) keeps a route as drawn in PowerPoint. Core composes them as `SlideComposition.overlayShapes`: overlay shapes as shape block items (`kind: "shape"`, SH-02's `ComposedShape`, text fitted by OPF's measured fonts) and connectors as `ComposedConnector`s routed as PowerPoint's `straightConnector1`, `bentConnector2`/`bentConnector3` and `curvedConnector2`/`curvedConnector3` with their `a:xfrm` frame and `a:avLst`, and the same route in slide coordinates. The preview draws overlay shapes with the shape block drawing and connectors with the shape stroke (dash, compound, sketch, arrowheads); the PPTX export writes overlay shapes as native `p:sp` and connectors as native `p:cxnSp` glued (`a:stCxn`, `a:endCxn`) to the shape blocks, overlay shapes, pictures and cards at their ends, so a connector follows a shape moved in PowerPoint. When `paginate` splits a slide, a shape placed by fractions is on every page, an `at` shape on its block's page and a connector on the page that holds both ends; a connector whose ends land on different pages is reported as `connector-split` in `PaginatedPage.diagnostics`. New findings: `opf/shape-anchor-missing` and `opf/connector-end-missing`; an overlay shape with both placements or none, a connector with a shape-only key, and a site index the shape does not have are `opf/schema` errors. Docs: `docs/shapes.md` ("Overlay shapes and connectors"); examples `examples/technical/shape-overlays.opf.json` and `shape-overlays-rtl.opf.json`.
- SH-06: shapes in the editor and the MCP. The editor inserts, restyles and adjusts shape blocks, each edit one undoable change: a shape picker (`@openpresentation/opf-editor/shape-picker`: `createShapePicker`, `createShapeMenu`; the playground's **Insert shape**, **Add content > Shape** and **Change shape…**) with PowerPoint's nine gallery groups, a tile drawn from each preset's geometry and a search by DrawingML name and common words; the yellow adjust handles on a selected preset shape (drag, arrow keys, Escape; fractions and degrees pinned to each handle's range); and a **Selected shape** section of the design controls (`shape` in `DESIGN_CONTROL_SECTIONS`) for the preset and its adjust values, fill (none, color, gradient, pattern), opacity, line (color or gradient, width, dash, cap, join, miter limit, compound, alignment, arrowheads, sketch), style, the six effects, rotation and flip, text, anchor, padding, direction, alt text, decorative, hidden and link, with Lighter and Darker tints on every color. `@openpresentation/opf-editor/shape-options` is the same from code: `insertShape`, `setShapePreset`, `setShapeAdjust`, `setShapeProperties` (each with a `prepare...` form), `searchShapes`, `shapeGroups`, `readShape`. A shape's outline is selected, not edited as text, when clicked; `createCanvasEditor` takes `shapeTools: false` to leave the handles out. Core gains `@openpresentation/opf/shape-catalog` (`SHAPE_CATEGORIES`, `SHAPE_CATALOG`, `searchShapeCatalog`, `shapeThumbnail`, `shapeThumbnailSvg`): the 187 presets in PowerPoint's gallery groups with their keywords. The MCP has a `search_shapes` tool (query, category, limit): each preset with its DrawingML name, group, default frame, adjust values (default, range, unit, whether a handle moves it) and a small SVG. See docs/shapes.md.
- SH-09: pyramids and matrices, written to PowerPoint as live SmartArt. A layout region's new `arrangement` (`"pyramid"` or `"matrix"`) draws its lone list of one level as a diagram, in the first design that holds every entry at one text size, the list's role size or larger, never smaller: PowerPoint's own geometry (Basic Pyramid of 1 to 8 levels, the first at the top; Basic Matrix of exactly four quadrants over a diamond), else OPF's own design of the arrangement (a stepped pyramid with each entry beside its level, or four quadrants filling the region). A matrix of other than four entries draws a grid of cards, and a list no design holds (or with nested entries, descriptions, icons or numbering) stays a list; both report the new info finding `opf/arrangement-adapted`. The gallery adds the `pyramid` and `matrix` layouts (32 layouts). Core exports the geometry and paint (`pyramidNodes`, `matrixNodes`, `pyramidSteps`, `matrixQuadrants`, `cardNodes`, `arrangementPaint`) and the domain PowerPoint was compared on (`SMART_ART_DOMAIN`, `smartArtUnavailable`); the preview draws the nodes under the entries. The PPTX export writes PowerPoint's design as live SmartArt where the instance lies in that domain: a `p:graphicFrame` with OPF's data model (explicit run sizes with `custT`, so PowerPoint keeps them), OPF's own colors and quick style parts, a drawing from core's geometry and no layout part (`r:lo` empty: OPF never writes a SmartArt layout definition); everything else, and everything with `smartArt: "shapes"` (CLI `--smart-art shapes`), is native `trapezoid`, `roundRect` and `diamond` shapes under the measured lines, with the info finding `pptx/smartart-unavailable` and its reason where live SmartArt was not written. Import reads an unchanged OPF SmartArt (`OPF_SMARTART_V1`) back as its list on its layout, and an edited one or a PowerPoint-authored Basic Pyramid or Basic Matrix from its data model (the nodes in `cxn` order with their run properties). See `docs/smartart.md`.
- The package READMEs of core, the CLI and the gallery gain a short section on shapes, icons, live SmartArt layouts and native Mermaid diagrams, and the gallery README documents the `@openpresentation/gallery/icon-sets` export (American spelling throughout). A new technical example, `icons-and-arrangements` (`opf create --example icons-and-arrangements`), draws icons from the Lucide and Tabler sets, the pyramid, matrix, cycle, chevrons, flow and vertical-flow layouts, and shapes joined by connectors. The opf-export skill describes the live slide-number field default (Header & Footer) correctly, and the opf-author and opf-inspect skills tell an agent to use the MCP server's `show_deck` to show a deck.
- RR-103: no third-party API names in OPF. The chart-type records no longer carry a `mappings.renderers` entry naming a vendor API (the `renderers` field stays in the schema as opaque renderer metadata), the schema descriptions define the supported chart types as those OPF renders and exports natively, and the PPTX chart table drops its vendor field. Chart types, records and exports are unchanged.
- SH-02 (breaking: picture `border` is now `stroke`, image `shape` names and `cornerRadius` changed): shape blocks. A block with `shape` (any of DrawingML's 187 presets: `chevron`, `rightArrow`, `wedgeRectCallout`, `flowChartDecision` and the rest) and no `image`, or with a custom `path` (SVG path data), draws the shape with optional `text` inside, and composes like any block: the largest frame of the preset's proportions (or `aspectRatio`) in its cell, its text fitted in the preset's text rectangle by OPF's measured fonts and never below `minFontSize` (`opf/text-overflow` at `<block>/text` otherwise). It takes `adjust` (the preset's handles in fractions and degrees), `fill` (`none`, a color, `{gradient}` with `type` linear, radial, rectangle or shape, `{pattern}`), `opacity`, `stroke` (color or gradient, width, preset or custom `dash`, `cap`, `join`, `miterLimit`, `compound`, `align`, arrowheads `start` and `end`, `sketch`), `style` (none, subtle, moderate by default, intense: PowerPoint's theme shape styles, written as `p:style`), `rotate`, `flip`, `anchor`, `padding`, `textDirection`, `alt`, `decorative`, `hidden` and `link`; the effect keys (`shadow`, `innerShadow`, `glow`, `softEdge`, `reflection`, `blur`) are in the format for SH-03 to draw. The preview draws core's evaluated geometry (SH-01) with every fill mode and stroke property, and draws gradients as PowerPoint 365 does (rectangle gradients as concentric rectangles and shape gradients along the outline, centered on the bounds of the filled paths, with PowerPoint's measured exceptions and its color mixing); a sketched line (`stroke.sketch`) is an outline core computes from a seed, which the preview draws and the PPTX stores in `ask:lineSketchStyleProps`, where PowerPoint draws it as stored. In a browser or edge bundle the preset geometry loads on demand (`ensureShapes`, `shapesPending`), so a deck without shapes or masked pictures beyond the four built-in masks does not carry it; the PPTX export writes a native `p:sp` with `a:prstGeom` (or `a:custGeom`), `a:ln`, `p:style` and the shape's own text body, never autofit. Every ColorRef also takes `{ "color": ..., "lighten": 0.4 }` or `{ "color": ..., "darken": 0.25 }` (PowerPoint's "Lighter 40%"), exported as `a:lumMod`/`a:lumOff` on the base color. An image block's line is `stroke` (renamed from `border`, no alias) with the same vocabulary, its `shape` takes every preset (`rectangle`, `rounded` and `circle` became `rect`, `roundRect` and `ellipse`) and `adjust` replaces `cornerRadius` (schema removals: `opf.schema.json:$defs.ImageBorder` and the old image `shape` enum, `opf.schema.json:$defs.ContentPayload.properties.shape`). New findings: `opf/shape-adjust-unknown`, `opf/shape-adjust-range`, `opf/shape-link-hidden`, `opf/shape-option-unsupported-payload`. Docs: `docs/shapes.md` (with the property map); example `examples/technical/shapes.opf.json`.
- Shapes phase 2 integration (SH-04 overlay shapes and connectors, SH-05 PPTX shape import, SH-06 editor shapes, SH-07 native Mermaid diagrams), where the four meet. One connector writer: the PPTX export writes SH-04's overlay connectors and SH-07's glued diagram edges as the same native `p:cxnSp`, glued with `a:stCxn` and `a:endCxn` to the native shape ids at core's connection site indexes (`shapeSites`; a diagram node of custom geometry has a rectangle's four sites in the same order). On import, a diagram group the export wrote (`OPF diagram N` with an intact `OPF_DIAGRAM_V1` manifest) is its Mermaid diagram again and none of its members become overlay shapes or connectors, also beside overlays in front of and behind it; an edited group imports as its shapes, as a PowerPoint deck's shapes do (the nodes as overlay shapes with their presets, fills, lines and text, the glued edges as connectors between them) and reports `invalid-diagram-provenance`. The grouped-text-reflow finding skips intact diagram groups. `docs/shapes.md` is one page: shape blocks, overlays and connectors, import, editing, native diagrams, then validation, loading, the preset geometry and the property map (with the overlay layer, connector middle and native diagram rows). The MCP's README lists `search_icons` and `search_shapes`; the editing skill names the editor release that has the shape APIs (0.33). ## 0.32.1 (2026-11-05)

- `validate_deck` checks diagrams in a Worker again. Since Workers take the lazy diagram engine, a hosted MCP server (`@openpresentation/mcp/server` on openpresentation.org/mcp) validated a deck before its diagram types were loaded and left out every diagram finding, such as a Mermaid syntax error; it now loads the types the deck draws (`ensureDiagrams`) before it validates, in JSON, YAML and Markdown, and reports what Node reports. ## 0.32.0 (2026-11-04)

- Diagrams: a new `diagram` content kind (on slide roots, blocks and layout regions; a string of Mermaid source, or `{ source, syntax, alt }`) draws flowcharts, sequence, class, state, ER, gantt, pie, mind map, timeline, journey, C4, architecture and the other built-in Mermaid 12.1 families with [pele](https://pele.run), in the deck's own fonts and colors. Core lays each diagram out with the deck's measured fonts at the largest size that fits its block, never below the readability floor (a diagram that only fits smaller is drawn smaller and reports a `text-overflow` finding with advice), and centers it; node fills, outlines and data series follow the slide variant and the chart palette, so dark slides and color maps adapt on their own. `alt` is the text alternative (without it engines derive one from the diagram's labels), a source that cannot be parsed reports a finding with its line and column and draws a "Diagram unavailable" placeholder, and a diagram takes a `caption`. A fenced block whose info word is `mermaid` is a diagram in Markdown (` ```mermaid alt="What it shows" `), written back losslessly. The PPTX export writes a native SVG picture over a PNG fallback (crisp, with `alt` as its description, round-tripping through `fromPptx`); the nodes are not yet editable PowerPoint shapes. Limits: 20,000 characters of source and 500 edges. Node, Bun, Deno and edge runtimes load every diagram type with core; a browser bundle loads pele's core (about 12 KB gzipped) and each type the first time a deck draws one, through the new `#diagram-engine` import map: the renderer's browser fonts handle loads them in `ensure` (and lists them in `pending` as `diagram:<type>`), `toPptx` loads them itself, and other hosts call `ensureDiagrams(presentation)` from `@openpresentation/opf/composition`. New fixtures: `examples/technical/diagrams.opf.json` and `examples/markdown/diagrams.opf.md`.
- LH-13 and LH-37 (docs and skills only, no drawing change): the `opf-author` skill gains a storyline guide (outline the titles first in one grammar, one idea per slide with a content-to-structure table, never invent a figure or a quote and how bracketed placeholders interact with `opf/placeholder-text`, speaker notes as a script, ask before adding slides or statistics), and the `opf-layout` skill gains a measured vertical budget (how many list entries, table rows and paragraphs keep the default size on a 16:9 slide, the `composeSlide` call that measures your own content, and when to split or paginate). `docs/default-catalog.md` gains a review checklist for gallery records against slide-design clichés.

## 0.28.0 (2026-10-26)

- New package `@openpresentation/mcp` (published with the set from 0.27.0): an MCP server for learning and validating OPF. Run it with `npx -y @openpresentation/mcp` (bin `opf-mcp`, stdio). Tools: `start_here` (a guided path for a goal: docs, skill, examples, layouts and themes, and the validate step with `failOn: "warning"`), `validate_deck` (the findings of `opf validate`), `get_schema` (a schema, a `$defs` name or a JSON Pointer), `search_catalog` and `get_catalog_record` (the default catalog and the example decks), `convert` (JSON, YAML and Markdown), `search_docs` (ranked, with snippets) and `list_examples`. Resources with stable URIs: `opf://docs/<slug>` (the user documentation, including the format card), `opf://docs/whats-new` (the last releases), `opf://schema/<name>[#<pointer or $defs name>]`, `opf://examples/<slug>`, `opf://catalog/<kind>/<id>` and `opf://skills/<name>`, each listed and readable through templates. Prompts: `learn_opf`, `author_deck`, `fix_validation_findings` and `choose_layout`. The server keeps no state and reads no file. Its definition is a library, edge-safe (no Node builtin, precompiled validators, bundled data; tested in workerd) for a hosted server: `@openpresentation/mcp` (with the bundled data) and `@openpresentation/mcp/server` (sources supplied by the host). See `docs/mcp.md`.
