## 0.33.0 (2026-11-08)

- LH-14: icons. An optional `icon` on a list entry (`items[].icon`), a metric (`metric.icon`) and a group (`icon` on a block with `blocks`) draws an icon on a chip, as Claude Design draws a feature list or a "what we will cover" card: in the marker column of a list (in place of the bullet, and of an agenda's numbered badges), above a metric, at the top start of a group. The value is `"<set>:<name>"` (`"lucide:truck"`), a bare name from the deck's new top-level `icons` map (an author's or an LLM's own SVG, written once), or an SVG source (`asset:<id>`, a relative path, an HTTPS URL or a data URI). Icon sets are a new catalog kind (`spec/schemas/icon-set.schema.json`, `catalogs.<group>.iconSets`): `@openpresentation/gallery` bundles Lucide (ISC, `lucide-static` 1.68.0) as the default set and Tabler outline (MIT, `@tabler/icons` 3.50.0), generated by `scripts/build-icon-sets.mjs`, with their licenses in each record and in the new `THIRD-PARTY-NOTICES.md`; the new entry `@openpresentation/gallery/icon-sets` exports `galleryIconSets`, a catalog to register beside `gallery` (`catalogs: [gallery, galleryIconSets]`) whose loaders import each set (`@openpresentation/gallery/icon-sets/<id>`) only when a deck uses it, so `gallery` itself carries no icon data; `ensureIcons(deck, { catalogs })` (core) loads what a deck names before the synchronous code reads it (`toPptx`, the renderer's browser `ensure`, core's `convert`, `opf validate` and the MCP call it; core's Node defaults, the CLI and the MCP register `galleryIconSets`). An SVG is read, never run: one paint makes a recolorable glyph (path commands in a 24 unit box), several a picture with its own colors; a script, event handler, external reference or raster refuses it. The chip is a light tint of the primary with the glyph in the primary (the inverse on a dark slide); it is a guarded drawing rule of composition (`icons` with compact chips a line high, `icon-chips` with chips 1.75 em across), so an icon never sets text smaller: a slide without room draws no chips. The preview draws SVG paths; the PowerPoint export draws a native ellipse and editable custom geometries in the theme's accent (`a:schemeClr val="accent1"`, the chip with lumMod/lumOff), so the icon recolors with the theme, and a multicolor icon as an SVG picture with its PNG fallback; import gives each `icon` back (OPF_ICON_V1 tags; the `icons` map travels in the document provenance). New findings `opf/icon-unknown` (with the nearest names), `opf/icon-invalid` and `opf/icon-dropped`; the MCP has a `search_icons` tool. New core exports: `ensureIcons`, `resolveIcon`, `parseIconReference`, `embedIcons`, `iconColors`, `iconFromSvg`, `iconPathCommands`, `iconPathData`, `placeIconCommands` (`/composition`), `SlideComposition.icons` and `ListEntryLayout.icon`. See docs/icons.md. Slides without icons compose and draw as before.
- SH-09: pyramids and matrices, written to PowerPoint as live SmartArt. A layout region's new `arrangement` (`"pyramid"` or `"matrix"`) draws its lone list of one level as a diagram, in the first design that holds every entry at one text size, the list's role size or larger, never smaller: PowerPoint's own geometry (Basic Pyramid of 1 to 8 levels, the first at the top; Basic Matrix of exactly four quadrants over a diamond), else OPF's own design of the arrangement (a stepped pyramid with each entry beside its level, or four quadrants filling the region). A matrix of other than four entries draws a grid of cards, and a list no design holds (or with nested entries, descriptions, icons or numbering) stays a list; both report the new info finding `opf/arrangement-adapted`. The gallery adds the `pyramid` and `matrix` layouts (32 layouts). Core exports the geometry and paint (`pyramidNodes`, `matrixNodes`, `pyramidSteps`, `matrixQuadrants`, `cardNodes`, `arrangementPaint`) and the domain PowerPoint was compared on (`SMART_ART_DOMAIN`, `smartArtUnavailable`); the preview draws the nodes under the entries. The PPTX export writes PowerPoint's design as live SmartArt where the instance lies in that domain: a `p:graphicFrame` with OPF's data model (explicit run sizes with `custT`, so PowerPoint keeps them), OPF's own colors and quick style parts, a drawing from core's geometry and no layout part (`r:lo` empty: OPF never writes a SmartArt layout definition); everything else, and everything with `smartArt: "shapes"` (CLI `--smart-art shapes`), is native `trapezoid`, `roundRect` and `diamond` shapes under the measured lines, with the info finding `pptx/smartart-unavailable` and its reason where live SmartArt was not written. Import reads an unchanged OPF SmartArt (`OPF_SMARTART_V1`) back as its list on its layout, and an edited one or a PowerPoint-authored Basic Pyramid or Basic Matrix from its data model (the nodes in `cxn` order with their run properties). See `docs/smartart.md`.
- SH-17: three more diagram layouts, `chevrons` (a row of chevrons), `flow` (boxes joined by arrows in a row) and `vertical-flow` (the same as a column beside the title), each a region's new `arrangement` value of the same name for one list of 1 to 8 stages or steps in order. See `docs/smartart.md`. - SH-18: cycles, written to PowerPoint as live Basic Cycle SmartArt. A layout region's `arrangement` takes `"cycle"`, and the gallery adds the `cycle` layout (33 layouts): its lone list of 1 to 8 entries draws as the steps of a loop, each a node on a ring with an arrow to the next, in the first design that holds every entry at one size, the list's role size or larger, never smaller. ## 0.32.0 (2026-11-04)

- Layout regions that hold a figure accept the new `diagram` kind: `charts` of `chart`, `chart` of `chart-beside`, `media` of `image`, `image-beside` and `hero`, `first` and `second` of `comparison` and `two-column`, the three columns of `three-column`, `steps` of `process` and `timeline` of `timeline`. A slide that pins a diagram to one of these regions, or binds one by kind, now places it there instead of reporting `region-kind`; no record draws differently.
- LH-01 (output-changing for slides on the section, statement, quote and closing layouts): a layout record can name a background variant in `design.variant`, either a variant or a value relative to the deck's own variant (`surface`: light2 on a light deck, dark2 on a dark one; `brand`: the brand dark, dark2, with light text; each takes the other slot where the deck is already on it). The default section draws on accent1, statement and quote on `surface` and closing on `brand`, so a dark deck keeps its tone. A layout's variant outranks the deck's and the theme's variant or background (it hides their background, and keeps the deck's accent order when it names none); the slide's own `design.variant` or `design.background` still wins. A variant's background can now be an accent (`accent1` to `accent6`, `ColorVariantSlot`): the accent is bg1 and bg2 and the text is the scheme's light family (light1, light2) or dark family (dark1, dark2), whichever reads better on it, with tx2 on tx1's slot where the family's tx2 is under 4.5:1. Core resolves it once (`resolveSlideContext` `resolved.roles` and `resolved.layoutVariant`, the validator's contrast checks, `composeSlide`'s background picture); the preview draws the variant's bg1 and the PPTX export writes the slide's `clrMapOvr` (`bg1="accent1"` for an accent) and imports it back as the variant its layout already gives. New on `/composition`: `layoutColorVariant(layout, deck)`, `layoutVariantApplies`, the `ColorBaseSlot`, `LayoutVariantRole` and `LayoutVariantDeck` types; `colorMapFor` takes the color scheme as a second argument for accent variants. The preview no longer paints a theme-slot background that sits beside a variant at the same level (`{ "background": "light1", "variant": "dark1" }` drew light text on white): the slide is the variant's bg1, as core and the PPTX export already resolved it.
  Drawing change (existing records that draw differently or are gone): `layouts:section`, `layouts:statement`, `layouts:quote`, `layouts:closing`.
- LH-06 and LH-68 (layout harvest; output-changing): one emphasis surface per slide, and scorecard metrics sized from their tiles.

- **`emphasis` on a block or group** (schema, core, render, PPTX). `emphasis: true` draws the block or group on the slide's emphasis surface: a card in its cell, with no card of its own for anything drawn on it. Its colors come from the deck's own scheme slots through the LH-01 variant machinery (new core `emphasisSurface`): on a light slide the brand dark (dark2, then dark1, then the accents), on a dark slide the accents in the slide's order, then light1, the first whose text reaches 4.5:1 on its fill and whose fill reaches 3:1 against the slide. Every text role on the surface (text, secondary text, primary, secondary, accent) under 4.5:1 is drawn in the surface's text color. A slide has one surface: the first `emphasis: true` in reading order takes it, any other is drawn without it and reported (composition diagnostic `emphasis-ignored`). Composition reports the surface as `SlideComposition.emphasis` (`path`, `box`, `radius`, `shape` card, band or pill, `source`) and marks every item on it `emphasis: true`; the preview and the PPTX export draw it from there (PPTX: a tagged `OPF card` frame with no line, imported as decoration), and `validate` measures the contrast of those items against the surface.
- **Automatic emphasis** (no authoring). On a slide without an authored emphasis, a short last text block (60 characters or fewer) after blocks that are all longer (any other kind, or text over 60 characters) is drawn as a full-width band at the foot of the body, and one of 30 characters or fewer after a lone long text as a pill one gap under that text's last line, at the start of its column (at the foot of the body when there is no room there). The body above composes in what is left, with a layout or without. **No block loses size to them**: the slide is also composed without the band or pill (what it drew before), the band or pill text starts at least at the size the block fitted at there, and the band or pill is kept only when it leaves fewer findings, or as many and no body block (text, list, any visible part of a quote, code panel, metric or timeline, a table's smallest cell) smaller. `emphasis: false` keeps a block out; a slide with an arrangement of its own (a `composition` mode other than auto, weights or columns) takes neither. Across the 844 slides of the LH-27 corpus, 8 take a foot band and 10 a pill; no slide gains a finding and no block gets a smaller size. Of the 360 composition goldens, 7 cases take a foot band (timeline, metrics, chart, chart-beside, table, table-beside and code with 2 short blocks), none gained a finding.
- **Metric tiles** (layout schema, core, gallery). A layout region's new `metrics: "tile"` lays each metric in it out from its whole cell: the label first as an eyebrow, the value under it asking for a quarter of the cell's height (between its 76 px role size and twice it, new `layoutMetric` option `tile`), a stacked unit under the value, and the description, delta and trend at the foot of the cell, start-aligned. Tiles fill their cards (no hugging) and siblings still share their sizes (LH-43). A tile never sets a role smaller than the metric fitted at as a stack (new `layoutMetric` option `minimumSizes`, from a stacked composition of the slide); where tiles would still cost a size or a finding, the slide keeps its stacks. The gallery `scorecard` layout's `cards` region uses it; its 12 composition golden cases moved, and across the corpus 18 metric values grow (76 to about 114 px) and none shrinks.
  Drawing change (existing records that draw differently or are gone): `layouts:scorecard`, `layouts:timeline`, `layouts:metrics`, `layouts:chart`, `layouts:chart-beside`, `layouts:table`, `layouts:table-beside`, `layouts:code`.

A lone list draws its entries beside badges down a connector, and a lone list of 3 to 6 entries of one or two words is a row of chips joined by arrows. In a `numbered` region (an agenda, which runs in time), every list draws beside badges, numbered or not: an unnumbered list is counted in arabic as drawing only, continuing across the region's lists (unless one of them cannot take badges), and the document and its PPTX import keep it unnumbered. Core reports the drawing as `SlideComposition.steps`, list entries as `ListEntryLayout.badge` (`fitList` option `badges`) and adds `listNumberLabel`, `STEP_BADGE`, `STEP_BADGE_GAP` and the `STEP_FLOW_*` limits. Import consumes those shapes and gives a list its numbering back. The gallery's `process` layout uses `steps`; `agenda` and `agenda-split` use `numbered`.
  Drawing change (existing records that draw differently or are gone): `layouts:process`, `layouts:agenda`, `layouts:agenda-split`.

## 5.0.0 (2026-10-21)

- **Breaking: layout records are one ordered list of regions; `areas`, `columns`, `rows` and the `regions` map are removed (FA-33).** A record is now `direction` (`"row"` or `"column"`, default `"column"`) and an ordered `regions` array of regions and splits. A region is `{ "name", "size"?, ...rules }` with the rules unchanged (`accepts`, `role`, `flow`, `max`, `bleed`, `listColumns`, `anchor`, `empty`); a split is `{ "direction", "regions", "size"?, "anchor"? }` and nests up to three levels. `size` is a weight (default 1) or `"auto"` (the height the content needs, in a column only), `title` and `subtitle` stay heading regions that take only `size`, `accepts` may be left out for every content kind, and an `anchor` on the record or a split applies to every region under it. All 28 layouts are converted, and each compiles to exactly the grid it had in 4.0.0 (areas, column and row weights, `auto` rows and every region rule, proven in `test/layout-equivalence.test.mjs` against a fixture of the 4.0.0 records), so no layout draws differently and the previews are unchanged. `quote` and `statement` write their `anchor: "middle"` once on the record. There is no old-format alias and no migration API: a custom layout in a deck must be rewritten. `CATALOG_SCHEMA` and `opf.catalogSchema` advance to `4`; the per-kind layout schema version stays `2` (`opf-layout/v2`). Records are validated by a core that reads this form, so this release needs the core release that accepts it.

- Build tooling: the one-release merged-engine bootstrap (`.github/bootstrap-engines.json`, `scripts/bootstrap-engines.mjs`) is generalized from "3.0.0" to the release the file names, with its catalog schema, and is set to 5.0.0 over the merged core (OpenPresentation/opf#756, `d223fc00`) and opf-render (opf-render#278, `e5838837`) commits, because core 0.25.0 cannot publish before it depends on gallery 5. The ancestry, digest and unchanged-manifest checks are as before. The layout-equivalence test compiles with core's own `layoutTemplate` (`@openpresentation/opf/composition`) instead of a test-local copy. The published package is unchanged by this tooling and stays dependency-free.

## 4.0.0 (2026-10-19)

- **Breaking: the `dark` theme is removed; dark is a variant of every theme.** Core 0.23.0 adds `design.variant`, a map over a deck's one color scheme (light1, light2, dark1, dark2, with an optional accent order). The `minimal`, `classic` and `bold` themes gain `variants` (`light`, `light-alt`, `dark`, `dark-alt`, each the value of `design.variant`), and the separate `dark` theme (the `boost` colors with the `seaford` fonts on `dark1`) is gone: a document that names `design.theme: "dark"` is an unknown theme (`opf/unresolved-reference`). Replace it with a theme and its dark variant, plus `colorScheme: "boost"` and `fontScheme: "seaford"` if the boost look is wanted. A removed id is a major release, so this is 4.0.0. No other record or drawing changes; `CATALOG_SCHEMA` stays 3.
- Development and CI use the published engines: `@openpresentation/opf` and `@openpresentation/opf-render` 0.23.0 replace the 0.19 pins and the one-release 3.0.0 bootstrap, which does nothing for any other gallery version. Core 0.23.0 derives borders, gridlines, axis lines, chart text and code colors from the color scheme, so seven layout previews are redrawn with `npm run previews` (this major release is where a redraw is allowed): chart, chart-beside, code, dashboard, table, table-beside and timeline. `previews/layouts/index.json` records their new sizes. No other record's drawing changes.
- The tests validate every theme's `variants[].variant` with core 0.23.0's `normalizeColorVariant` and `isColorVariant` (`@openpresentation/opf/composition`) instead of a hand-written shape check.
